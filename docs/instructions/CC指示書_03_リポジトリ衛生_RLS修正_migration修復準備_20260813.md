## 1. 運用原則（全フェーズ共通・違反は差し戻し）

- **実行と検収の分離**：完了判定は検収者（人間側）が実在で行う。自己申告で完了扱いにしない
- **実在検収**：完了報告には実行結果の実物（コマンド出力・ログ・SQL実測値）を引用する。
  証跡のない完了報告は再提出
- **fail-closed**：判断に迷う操作・想定外の状態に遭遇したら、進めずに停止して報告する
- **本番反映はCI経由のみ**：本番Project Ref `kwpldqbnkraftaahnpev` へのCLI直接操作は絶対禁止
- **凍結継続**：`supabase migration repair`／`DELETE FROM supabase_migrations.schema_migrations`／
  `supabase db push` は、人間の合図があるまで実行しない（ローカル環境への `db push` を除く）
- **CI監視の定型化**：push後はGitHub Actions全ジョブ＋VercelチェックをghでComplete まで自律監視し、
  「全ジョブ結果＋実行実態証跡（skip有無・実行時間・接続先）」を定型報告する
- **人間作業のバッチ化**：人間側の作業が必要になったら、ブロッカーでない限り即依頼せず、
  パートの区切りでまとめて依頼する

## 3. フェーズ1：リポジトリ衛生とガード強化

### ① 未コミット107ファイル差分の精査とコミット分離

- `git status` / `git diff` で**全数**確認する。サンプリングでの精査は不可
- 内容別にコミットを分離する：
  1. hooks修正（`$CLAUDE_PROJECT_DIR` 化）
  2. 診断キット（`docs/runbooks/2026-08-12_migration-state-diagnosis.md` ほか関連）
  3. gotchas追記（`.claude/skills/` 配下）
  4. prettier整形（**整形のみのコミットとして分離**。実質変更を混ぜない）
- 上記4系統に分類できない変更が見つかった場合は、コミットせず内容を報告して指示を待つ
  （例外：本指示書 `docs/instructions/CC指示書_03_*.md` が未追跡で存在する場合は、
  独立した1コミットとして追加してよい）
- 各コミット前に `git diff --staged` で混入がないことを確認し、確認結果を報告に含める

### ② hook迂回の再発防止

- `.claude/settings.json` のhooks matcherを精査し、**ファイル書き込みに到達しうる全ツール**
  （Write / Edit / NotebookEdit / Bash に加え、Monitor等の間接経路・サブエージェント経由を含む）が
  hooks対象になるよう修正する
- ツール名matcherで対応しきれない経路（例：matcherの仕様上フックできないツールやイベント）が
  残る場合は、**その事実と制約を `docs/rules/` 配下に追記して顕在化**させる。黙って残さない
- 修正後、両コントロールを**実物引用**で証明する：
  - 陽性コントロール：通常のファイル書き込み操作がpassすること（hook実行ログを引用）
  - 陰性コントロール：(a) 本番Ref `kwpldqbnkraftaahnpev` への操作がblockされること、
    (b) 従来の迂回経路（Monitor等）経由の書き込みがblockされること（block時の実出力を引用）

## 4. フェーズ2：RLS監査3指摘の修正＋CI完全化

### ① WITH CHECK欠落の修正（新規migration 00019）

- 全テーブルのINSERT/UPDATEポリシーに適切な `WITH CHECK` を追加する新規migration
  `00019` を作成する
- 特に `events` / `known_explanations` の「任意の認証ユーザーが `company_id = NULL` で
  INSERT可」を遮断する
- NULLスコープ行（S0読み取り用）の**読み取り**は設計意図どおり維持し、
  **書き込み**は `service_role` 限定にする
- 冪等に書くこと（再実行安全。`DROP POLICY IF EXISTS` → `CREATE POLICY` 等）
- ローカル `supabase db reset` で00001〜00019が通ることを確認（これはローカルなので凍結対象外）

### ② rls.test.ts のfail-open修正

- 現状の `exec_sql` RPC不在時に**passしてしまう空パス**を、**failする**よう修正する
- RLS有効性の検証を**実クエリベース**に書き換える：越境SELECT / INSERT / UPDATE / DELETE が
  **実際に拒否されること**を確認するテストにする
- 2社分のダミーユーザー（company A / company B）を作成し、陽性（自社データ操作が成功）・
  陰性（他社データ操作が拒否）の両方向を検証。**3回連続で再現**することを確認し、実行ログを引用

### ③ CIのRLSスイートskip解消

- `.github/workflows/ci.yml` にローカルSupabase起動（`supabase start`）＋
  `SUPABASE_*` 環境変数の注入を追加し、integrationテストが**skipなしで実行される**状態にする
- `deploy-functions` の `npm:` 指定変更も、このCIで検証されることを確認する

### ④ push → CI/Vercel自律監視 → 証跡報告

- フェーズ1・2の成果はfeature branchにpushし、PRを作成する
  （契約基準の全passなくmerge禁止の原則に従い、**mainへの直接pushはしない**。
  mergeの判断は検収者が行うため、CI緑の確認・報告まで進めて停止する）
- push後、GitHub Actions全ジョブとVercelチェック（`gh pr checks` / `gh api`）を完了まで自律監視
- 報告に含めること：全ジョブの結果／skipの有無／各ジョブ実行時間／
  **RLSテストが実際に実行された証跡**（CIログの該当行引用：テスト件数・接続先）
- CI失敗時：コード側で解決可能なものは自己修正→push→再監視まで自律で回す。
  Dashboard設定・秘密・課金に触る対応が必要な場合のみ停止・報告
