### 1. `/api/connections` の未認証アクセス — **クローズ済み（2026-08-18、スライスA）**

**状態: 解消。** 認証スライス（`docs/contracts/slice-auth-ui.md` A-2）で塞いだ。

当時の指摘: `src/app/api/connections/route.ts` は認証を持たず、`company_id` をクエリパラメータで
受け取り、**service_role キー**で `connections` と `events` を読んでいた。
RLS をバイパスするため、company_id を知る／推測できる第三者が
任意の会社の接続状態とイベント件数を取得できた。

対処:

- `GET /api/connections` は引数を取らなくなった。company_id をクエリパラメータで受け取る経路が
  構造的に存在しない。company_id はセッション（`auth.uid()`）から導出する

  越境はアプリだけでなく RLS でも止まる（二重化）
- 未認証は 401

**調査で判明した追加分**: 同じ「クライアント供給の company_id を無検証で信用する」形は
`/api/connections` だけでなく5本あった。読み取りだけでなく**他社への書き込み**も通っていた。
いずれも同時に塞いだ。

| ルート                    | 当時の受け取り方                    | 影響                                                 |
| ------------------------- | ----------------------------------- | ---------------------------------------------------- |
| `api/connections`         | クエリparam                         | 他社の接続状態とイベント件数の読み取り               |
| `api/csv/ingest`          | JSON body                           | 他社スコープへの events 書き込み                     |
| `api/competitors/suggest` | JSON body                           | 他社スコープへの entities 書き込み                   |
| `api/auth/google`         | クエリparam を OAuth `state` に流用 | 他社への接続紐付け／state がCSRFトークンとして無機能 |
| `api/auth/freee`          | 同上                                | 同上                                                 |

OAuth の `state` は 32バイトの乱数に変え、httpOnly cookie と照合するようにした。

固定テスト: `tests/unit/connections-api-auth.test.ts`（未認証401）、
`tests/integration/connections-api.test.ts`（2ユーザー2社の実クエリによる越境不可）。

### 2. カレンダーの件名・出席者メールを `events.metrics` に保存している（製品判断）

`src/app/auth/callback/google/route.ts` の同期処理は、取り込んだ予定について
`metrics: { title, attendees }` を保存する（`sensitivity: "S1"`）。
件名の文字列と出席者のメールアドレスがそのまま DB に載る。

**両論併記（判断は人間）:**

- **保存してよい側の論拠**: allowlist のカラム名規則には抵触しない（`metrics` は
  JSONB の許可カラムで、禁止パターン `body|content|text|message|subject` は
  カラム名に対する規則）。件名はパターン検出（会議の沈黙・頻度変化）の
  精度に直結し、Sense層の質を上げる。S1 として分類済みで、RLSで会社スコープに閉じている。
- **保存すべきでない側の論拠**: 製品の担保として掲げている「**本文非取得**」に対し、
  会議の件名は実質的に本文に近い。出席者メールは個人情報であり、
  取引先の実名露出（本ファイル「事業判断待ち」の既存項目）とも地続き。
  Findingの根拠提示で件名が画面に出ると、ユーザーの期待と食い違う可能性がある。

**選択肢**: (a) 現状維持 (b) 件名をハッシュ／長さ等の派生値に置換
(c) 出席者はドメインのみ保持 (d) 件名は保持するがFinding表示には使わない

## `check:allowlist` のCI空洞 — 修正タスク（2026-08-18 登録・本PRでは修正しない）

CLAUDE.md絶対規則「S2テーブルに本文型カラムを追加しない（allowlist外カラムのマイグレーション禁止）」は、
CIジョブ `verify` の `pnpm run check:allowlist` で担保されている**建て付けになっているが、実際には担保されていない**。

**実測（run 32134357004 / job 95702233426）:** このstepの出力は
`check:allowlist — run against live DB` の**1行のみ**。`scripts/check-allowlist.ts` のCLI入口は
`console.log` だけで、実DBの `information_schema.columns` を照会していない。
純粋関数 `validateS2Columns` は `tests/unit/allowlist.test.ts` の3ケースで検証済みだが、
**その関数を実スキーマに当てる経路が存在しない**ため、allowlist外カラムが本番に入っても
CIは必ず緑になる。

### 判断が要ること

1. **どのDBに当てるか。** ローカル（`supabase start`）／CIのSupabaseサービスコンテナ（`integration`
   ジョブは既にDB接続を持ち、8ファイル44テストをskipなしで実行できている）／本番read-only の3択。
   本番Refへの直接操作はCLAUDE.md絶対規則で禁止のため、実行するならCI経由に限る
2. **どのジョブに置くか。** 現状 `verify` にあるがDB接続を持たない。`integration` 側へ移すのが素直だが、
   その場合「S2規則違反の検知」が統合テストの成否に混ざる
3. **失敗時の扱い。** allowlist違反はマイグレーションのmerge阻止条件なので、fail-closed（ジョブ失敗）とする

### 暫定の扱い

修正までの間、S2スキーマ変更は `.claude/skills/migration` の手順と schema-reviewer の

**原因（実装どおりで、故障ではない）:**

- `markReauthRequired` を呼ぶのは `supabase/functions/_shared/token-refresh.ts` の

- `supabase/functions/sync-connections/index.ts` の同期本体が投げた例外は

  `connections.status` を触らない
- 期限判定は `EXPIRY_BUFFER_MS = 5 * 60 * 1000`

### 判断が要ること

1. **401 だけを対象にするか。** 403（スコープ不足・APIが無効）や 429 を巻き込むと、
   一時的な事象で「要再連携」を出して利用者に不要な再連携を強いる。
   Sentio は入力を求めない製品なので、**誤検知のコストは取りこぼしより高い**
2. **どこで落とすか。** 同期関数それぞれに置くと重複する。
   `token-refresh.ts` と同じく共有ヘルパーに寄せるのが素直
3. **fail-closed の向き。** 401 を受けた回数で落とすか、1回で落とすか。
   Google 側の一過性 401 を踏むと、1回で落とす実装は誤検知しやすい

**着手前に必要なもの:** 実装より先に、401 を返す接続を作る統合テスト。

## cron の HTTP 応答を誰も読んでいない（2026-08-20 登録・**未解決**。2026-08-31 に射程を更新）

> **2026-08-31 追記（スライスCD）— この穴は埋まっていない。**
>
> ディスパッチャ（`dispatch-daily` / `dispatch-weekly`）を作ったことで**性質だけが変わった**。
> 「ディスパッチャを作ったので cron の穴は埋まった」と読まないこと。
>

> | ------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------- |
> | **変わったこと**   | `deliver-*` / `run-sense` の失敗は**ディスパッチャが `await` して掴む**ようになった。全社の結果を集計し、1件でも失敗があれば non-2xx を返す（CD-2-2）   |

## 列名の行が2行目以降にあるCSV（未判断・2026-08-31 登録・スライスCH の残余）

スライスCH の判定は**1行目だけ**を見る（CH-D4）。
したがって**1行目がタイトル行、2行目が列名**という形は**検出できない**。
通れば `○○銀行 入出金明細` のような1行目がプロンプトに載る。

列数の食い違い（1行目だけセルが極端に少ない）で検出できる見込みはあるが、

### 判断が要ること

1. **2行目を読むか。** 1行目との列数比較には2行目が要るが、**2行目はデータ＝PII である。**

   「判定のためにどこまで読むか」は線を引いておく必要がある
2. **前置き行を飛ばして取り込むか、断るか。** 飛ばせば使えるようになるが、
   何行飛ばすかを機械が決めることになる。CH-D1 と同じ「対応せず断る」で揃えるのが素直

**この形の実物はまだ出ていない。** 出ていない段階で判定を足すと、
CH-2 系（誤検知を出さない）の側が先に壊れる。実物が出てから決めるのが順序である。

解約・プラン変更のボタンは置いていない（BU-D4）。

置かなかったのは、解約が**画面を1つ足す話ではない**からである。
Stripe カスタマーポータルのセッションを作るエンドポイント（`billingPortal.sessions.create`）と、
戻り先の扱いが要る。購読の開始（1本）と同じ手数では終わらない。

### いま利用者が解約するには

**Sentio の外で行うことになる。** 支払い時の Stripe のメール（領収書）から
顧客ポータルに入るか、問い合わせを受けて手作業で止めるかである。
**どちらも画面には書いていない。**

### 判断が要ること（**勝手に確定させない**）

1. **カスタマーポータルを使うか、自前で作るか。** ポータルなら Stripe 側の
   設定画面で解約・支払い方法変更の可否を決めることになり、**文言も Stripe のものになる**
2. **解約したあと、いつ枠が下がるか。** `lib/billing/plan.ts` は
   `canceled` を既定（いまは標準）に落としている。期末まで使えるのか、即座に下がるのかは、
   `DEFAULT_PLAN` を試用に倒す判断（`09_pricing.md` の非スコープ）と同時に効く
3. **特定商取引法に基づく表記の「解約条件」と揃うか。** 有償化の時点で掲示が要ることは
   このキューに登録済みで、**掲示する解約条件と実際の導線が食い違ってはいけない**

### 着手の合図

**最初の1社が購読したとき。** 購読者が居ない間は、止める導線が無くても誰も困らない。
逆に1社でも入ったら、**止められないことは約束の問題になる。**

## `trialing` を購読中と見なすか（未判断・2026-09-03 登録・スライスBU）

**いまは `active` だけを購読中として扱っている**（契約 BU-1-2 のとおり）。
Stripe が返す `trialing` は、画面では**試用中の側に落ちる**——
つまり**購読ボタンが出たままになる。**

```ts
// src/app/connect/connect-client.tsx
const subscribed = subscriptionStatus === "active";
```

枠を与える判定（`src/lib/billing/plan.ts` の `ENTITLED_STATUSES`）は
`active` と `trialing` の両方を通す。**画面と枠で見ている集合が違う。**

### いま実害が無い理由

**Stripe 側の trial を使っていない。** `09_pricing.md` の「まだ決めていないこと 3」で
試用の期間そのものが未決であり、Sentio の試用は「購読が無い状態」＝0円/5回として
表しているので、`trialing` は現状どこからも書き込まれない。

### 判断が要ること（**勝手に確定させない**）

1. **Stripe の trial を使うか。** 使うと決めた日に、この行が**二重購読の入口になる。**
   trial 中の会社に「標準プランにする」を見せることになり、押せば2本目の購読ができる
2. **画面と枠で集合を揃えるか。** 揃えるなら判定を1か所（`plan.ts` 側）に寄せる。
   揃えないなら、**なぜ違うのかを両方に書く**

### 着手の合図

**`09_pricing.md` の「試用の期間」を決めるとき。** trial を Stripe 側に持たせる判断を
した時点で、この項目は未判断ではなく**バグ**に変わる。

## `?billing=done` で戻った直後、まだ「試用中」に見える（**外部顧客に出す前の必須項目**・2026-09-03 登録）

**3万円を払った直後の画面に、購読ボタンが出たままになりうる。**

`/connect?billing=done` は Stripe の `success_url` である。戻ってくるのは
**支払いが済んだ直後**だが、`user_metadata.subscription.status` を `active` にするのは
**webhook** であり、決済の完了と webhook の到着は**別々に起こる。**
webhook が着く前にこの画面を描くと、状態の正本はまだ空で、
画面は契約どおり「試用中」＋「標準プランにする」を出す。

**見た目の問題ではない。** 払った直後の人に購読ボタンを見せれば、
**二重に払う人が出る。** `/connect?billing=done` は「払った直後」だと分かっている
唯一の場所なので、そこで何も言わないのが問題である。

### なぜ今回やらなかったか

スライスBU の非スコープ。契約が定めた状態は2つ（試用中／購読中）だけで、
**「払ったが、まだ反映されていない」は3つ目の状態**である。
`billing=done` を読むだけでは足りず、
「webhook を待っているのか、失敗したのか」を切り分ける設計が要る。

### 判断が要ること（**勝手に確定させない**）

1. **3つ目の状態を置くか。** `?billing=done` のときだけ購読ボタンを引っ込め、
   「確認しています」と出すのが最小の案。**ただし webhook が永久に来なければ
   永久にそう出る**ので、待つ時間の上限と、そこで何を出すかが要る
2. **待たずに確かめに行くか。** 戻り先で1度だけサーバ側から Stripe に問い合わせれば
   確実だが、**BU-D2「画面から Stripe API を叩かない」と正面からぶつかる。**
   叩くならサーバ側の1回に限り、正本は依然 webhook が書く値とする、という整理が要る

### 期限

**外部顧客に出す前に必ず潰す。** 最初の1社が購読するより前である
（`docs/spec/07_open_items.md` の「解約の導線が無い」と同じ合図）。
