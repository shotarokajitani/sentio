# Finding が0件である構造的な理由（2026-09-03・検収者）

**毎朝届くパルスが「状態: 平常」しか言わないのは、データが少ないからではない。
走査8本のうち5本は、本番に入力が存在しないので永久に発火しない。**

## きっかけ

スライスCD が閉じ、配信が自動で回り始めた（8/31・9/1 実測）。
そこで毎朝届いているのはこれである。

```
2026-09-01: 1件のイベントを記録
主な種別: schedule
状態: 平常
```

品質基準は「読んだ経営者の頭に、自社の状態が一枚の絵として浮かぶか」である。**浮かばない。**
契約CD の「この契約が閉じたら分かること」が予告したとおり、
**中身が薄いことが毎日目に入る**状態になった。そこで中身の側を調べた。

## 断定できること — **`metrics.revenue` を書く取り込み経路が1つも無い**

`supabase/functions/_shared/scan.ts:134`（走査1・乖離）と
`supabase/functions/state-baselines/index.ts:49`（revenue ベースライン）は、
どちらも `metrics.revenue` を読む。

**書いている場所を全部見た。**

| 経路            | 実際に書いている `metrics`                    | 出所                                      |
| --------------- | --------------------------------------------- | ----------------------------------------- |
| Google Calendar | `{ title, attendees }`                        | `sync-connections/index.ts:238`           |
| freee           | `{ description, amount, deal_type }`          | `sync-connections/index.ts:325`           |
| 入出金CSV       | `{ description, amount, direction, balance }` | `src/app/api/csv/ingest/route.ts:184-189` |

**`revenue` は1つも無い。すべて `amount` である。**

したがって:

- `state-baselines` が集める `revenues` は**常に空**。`MIN_OBS = 5` 以前の問題で、観測が0
- revenue ベースラインは `is_established` にならない
- 走査1（乖離）は `established` を回すループに入らないので、**1件も候補を出せない**

**59行のCSVを入れても、走査1は動かない。**入れる量の問題ではない。

## 評価スイートが緑だった理由（**前と同じ形**）

`scripts/generate-synthetic-company.ts:68`

```ts
metrics: { revenue, amount: revenue, description: `Month ${m + 1} revenue` },
```

**合成会社は `revenue` と `amount` の両方を書いている。** 本番の取り込みは `amount` だけ。
評価スイートは、**本番が生成しないキーを供給して緑になっている。**

`scan.ts` の冒頭コメントが記録している事故と同じ質である。

> 評価スイートは `src/sense/scanner.ts` という**本番で走っていない別実装**を測り続けていた。
> 6週間、製品の中核が測られないまま「5/7」という数字だけが出ていた。

**あのときは「別の実装を測っていた」。今回は「同じ実装を、本番に無い入力で測っている」。**
実装は揃えたが、**入力を揃えていなかった。**

## 実測による訂正と追記（2026-09-03・CC 測定）

上の表は **6 を「発火しうる」としたが、誤りだった。** 実測で3点分かった。

### 1. 走査6 も現状は発火しない

`baselines` に存在する行は**1件だけ**である。

```
metric_key  granularity  is_established  min_obs  stats->>'count'  最終更新
revenue     event        false           5        null             2026-08-27 09:59:46+00
```

**`schedule_interval` の行が存在しない。** `state-baselines/index.ts:103` が書くはずのキーが、
本番に1行も無い。走査6 は `is_established` なベースラインを前提にするので、**回らない。**

したがって**発火しうる走査は、実質 7・8 の2本だけ**である。

### 2. その2本も、条件を満たしていない — **ただし閾値のせいではない**

- `schedule` は系列が育たず対象外（同一 `title` が4件に届かない）
- `transaction` は**対象になっている**。しかし
  - **途絶**: 最後の取引が3日前、平常が5日間隔。**系列は生きている**
  - **伸長**: 間隔が 1〜29日と散らばっており、**単調増加ではない**

**「検知条件が厳しすぎて取りこぼしている」のではない。検知すべき変化が起きていない。**
`SERIES_MIN_INTERVALS` を下げる根拠にはならない。**下げてはいけない。**

### 3. `state-baselines` が 2026-08-27 以降走っていない

`baselines` の最終更新が 08-27 で、その後 `events` は増えている（最新 09-02）のに更新がない。
**定期実行されていない可能性がある。** 走査6 の可否とは別の問題として切り分けが要る
（`cron.schedule` が張られているのは `sync-connections` と `dispatch-*` だけ、という
契約CD の記述と整合する。**`state-*` を回す経路が設計に無い**）。

## 問いが変わった

当初の問いは「なぜ検知が0件なのか」だった。実測の答えはこうである。

- **走査の大半（1〜5）は、本番に入力の型が存在しない**
- **走査6 は、ベースラインを書く経路が回っていない**
- **動く走査7・8 の対象データには、検知すべき変化が起きていない**

3つ目が重要である。**顧客0号（自社）は健全で、いま異常が無い。**
異常が無い会社に異常を報告させることはできない。**閾値を下げれば嘘が出るだけである。**

したがって本当の問いはこれになる。

> **何も起きていない会社に、Sentio は何を言うのか。**

品質基準は「読んだ経営者の頭に、**自社の状態が一枚の絵として浮かぶか**」であって、
「異常が報告されるか」ではない。**いまのパルスは異常検知の器しか持たず、
状態を記述する器を持っていない。** だから異常が無い日は「平常」の1語しか出ない。

**これは検知器の不足ではなく、出力の設計の不足である。**

## まだ断定できないこと（**測っていない**）

走査7・8 が本番で0件なのは、次のどちらなのかが分かっていない。

- **(a) シリーズが4件に届いていない。** CSV 59行の摘要が散っていて、
  同じ相手が4回以上現れないなら、間隔が3つ取れず対象外になる
- **(b) シリーズはあるが、条件（単調増加 / 平常の3倍）を満たしていない**

**(a) なら「データが足りない」、(b) なら「検知条件が厳しすぎる」で、打ち手が正反対である。**
推測で決めない。次に測る。

### 測るもの（CC への依頼）

本番の `events` に対して、次の3つの数だけ取る。**本文は取らない。件数だけ。**

1. `event_type` ごとの件数と、最古・最新の `occurred_at`
2. `transaction` を `metrics->>'description'` で束ねたときの、**件数が4以上の系列の数**
3. `schedule` を `metrics->>'title'` で束ねたときの、**件数が4以上の系列の数**
4. `baselines` の行（`metric_key` / `is_established` / `stats->>'count'`）

**摘要そのもの（取引先名）は出力に含めないこと。** 件数と分布だけで判断できる。

## 判断が要ること（**勝手に確定させない**）

1. **`revenue` を何と定義するか。**
   `amount` をそのまま `revenue` と読み替えることはできない。
   CSV の `amount` は**出金が負**の符号付きで、freee は `deal_type` を別に持つ。
   「売上」を入金だけとするのか、`deal_type === "income"` だけとするのか、
   **会計上の売上と現金の入金を区別するのか**が決まっていない
2. **走査2〜5 を残すか。**
   入力が存在しない走査が5本ある。消すのか、取り込み側を足すのか、
   **「いまは死んでいる」と明記して残すのか**。
   黙って残すと、次に読んだ人が「8本の検知がある」と誤読する
3. **シリーズの最低本数（`SERIES_MIN_INTERVALS = 3`）を下げるか。**
   下げれば発火しやすくなるが、平常が定まらない系列で誤検知する。
   **測ってから決める**（上記 (a)/(b) の切り分けが先）

## この報告が主張しないこと

**「データを増やせば直る」とは言っていない。**
走査1〜5 はデータを100倍にしても0件のままである。**入力の型が無いからである。**

逆に **「検知が壊れている」とも言っていない。**
走査7・8 は本番の鍵（`title` / `description`）を見るように既に直されている（`scan.ts:65-68`）。
動きうる2本が実際に何を見ているかは、上の測定で分かる。
