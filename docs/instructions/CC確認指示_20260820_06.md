あなたは `0085b78` で runbook と SQL を作りました。**契約書の本文だけが更新されていません。**

節の見出しは「merge 前の停止点」なのに、本文が「デプロイ後に実測する」と書いてある。
**読んだ人が「停止点2 は merge を止めない」と解釈できてしまう状態**です。
このプロジェクトが繰り返し踏んでいる「宣言と実態のずれ」と同じ形です。

### 書き直す形

停止点2 を**2段に分けて**ください。混ぜないこと。

**2-a. 静的一致（merge 前。merge を止める）**

- 目的: cron が送る `Authorization: Bearer` の値と、プロジェクトの現行 service_role キーが
  **同じ値か**を、**関数を1回も呼ばずに**確かめる
- 手順の実体: `docs/runbooks/2026-08-20_cron-bearer-key-match.sql` と
  `docs/secrets-runbook.md`「service_role キーの保管先は3箇所ある」
- 合格条件: `key_len` / `key_tail` / `key_sha256` の3つがすべて一致
- **`key_prefix` が `eyJ` 以外だった場合は merge を止めて相談**（新形式がゲートウェイの
  `verify_jwt` を通るかは未実測）
- **なぜ merge 前なのか**を本文に書くこと。17本すべてから `--no-verify-jwt` を外した以上、
  不一致のままデプロイすると唯一稼働している `sync-connections` が毎日 401 で止まる。
  かつ `net.http_post` は非同期なので `cron.job_run_details` は succeeded のまま
  ＝**止まっていることがどこにも出ない**

**2-b. 実疎通（デプロイ後。A-2 を止める）**

- `net._http_response.status_code` が **200** であること
- 保持期間が短い（既定で数時間）ので **cron 発火の直後に見る**。
  発火は JST 9 / 15 / 21 / 3 時（`0 0,6,12,18 * * *` UTC）
- 刈られていた場合の代替は Dashboard の `sync-connections` の Invocations / Logs
- **`cron.job_run_details` では判定できない**ことを引き続き明記する
