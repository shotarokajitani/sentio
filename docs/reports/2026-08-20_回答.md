## Q1. workflow_dispatch を merge 前に実行できない理由

### 答え: **Yes**

「ワークフローファイルがデフォルトブランチに存在しないとディスパッチできない」で合っている。

### 根拠（実測。gh CLI と REST の両方を実際に叩いた）

gh CLI 経由。`--ref` でブランチを明示しても弾かれる。

```
$ gh workflow run invoke-function.yml --ref slice-state-repair \
    -f function_name=__probe__ -f body='{}'
HTTP 404: workflow invoke-function.yml not found on the default branch
  (https://api.github.com/repos/shotarokajitani/sentio/actions/workflows/invoke-function.yml)
```

**エラー本文が「not found on the default branch」と明示している。**
gh の作文ではなく、REST を直接叩いても同じ 404 が返る。

```
$ gh api -X POST \
    repos/shotarokajitani/sentio/actions/workflows/invoke-function.yml/dispatches \
    -f ref=slice-state-repair -f 'inputs[function_name]=__probe__' -i
HTTP/2.0 404 Not Found
{"message":"Not Found",
 "documentation_url":"https://docs.github.com/rest/actions/workflows#create-a-workflow-dispatch-event",
 "status":"404"}
```

### 補強証拠: GitHub 側にワークフローとして登録すらされていない

```
$ gh api repos/shotarokajitani/sentio/actions/workflows
306063499 | ci                 | .github/workflows/ci.yml
332435475 | deploy             | .github/workflows/deploy.yml
332435588 | Dependabot Updates | dynamic/dependabot/dependabot-updates
```

`invoke-function` が居ない。デフォルトブランチの中身とも一致する。

```
$ git ls-tree -r origin/main --name-only .github/workflows/
.github/workflows/ci.yml
.github/workflows/deploy.yml
```

`invoke-function.yml` はこのブランチ（slice-state-repair）にしか存在しない。

### 安全性について

`function_name` に `__probe__` を渡したのは意図的である。`deploy.yml` のデプロイ対象に
存在しない名前なので、仮に 404 でなく起動していたとしても S-4-10 の許可リスト検査で止まる。
**実 Edge Function は一度も叩いていない。**

## Q3. S-5 はなぜ「完了」と報告されたのか

### 答え: 「そのとき実行したコマンドと出力」は提示できない。存在しないため

前セッションのトランスクリプトを私は保持していない。
そして後述のとおり **`check:schema` はこのローカル環境で原理的に実行不可能**である。

「確認漏れ」で片付けるなという指示なので、**なぜ構造的にそうなるか**を実測で示す。

### 実測1: `check:schema` / `check:allowlist` はこの環境で走らない

psql が無く、Docker デーモンも起動していない。
**この2本は CI の integration ジョブ以外では一度も走らない。**

### 実測2: 一方で、ローカルで走る検査は当時も今も全部緑である


### 機序

**S-5 の完了判定に使えたのは「ローカルで走る検査」だけで、S-5-1 の判定器は
その集合の外にあった。**手元が全部緑になった時点で完了と報告した、という構造である。

これは第3便【3】の分類でいう #2（CI で走って赤なのに完了報告）だが、
根にあるのは「ローカルで回せる検査の集合 ≠ 完了判定に必要な検査の集合」というずれで、
#1（deno check 28件）と同じ形をしている。deno check も、`tsconfig.json` が
各 Function の `index.ts` を除外しているため `pnpm typecheck` では一切見えない検査だった
（`ci.yml:158-160` のコメントが同じことを書いている）。

### 再発を止める条件

CLAUDE.md 常設指示「CI監視の定型化」（push 後は CI 全ジョブの完了を自律監視し、
完了時に全ジョブ結果を定型報告する）は**既にそう書いてあり、守られていなかった**。
新しい規則ではなく、既存規則の履行が要る。

なお、この穴は第3便【3】の #2 に対応するもので、Q4 の照合スクリプトでは捕まらない
（#1 / #3 の担当）。両方要るというあなたの整理は正しい。

## Q8. グローバルフックと、その対処案

### Q8-b. `~/.claude/settings.json` のフック定義（引用）

**読み取りのみ。書き換えていない。**

トップレベルキーは7つ。

```
permissions
hooks
enabledPlugins
extraKnownMarketplaces
autoUpdatesChannel
tui
autoMode
```

`hooks` セクションは**これで全文**である。定義は1イベント・1 matcher・1コマンドのみ。

```json
{
  "PostToolUse": [
    {
      "matcher": "Write|Edit",
      "hooks": [
        {
          "type": "command",
          "command": "npx prettier --write . 2>/dev/null; true"
        }
      ]
    }
  ]
}
```

| 項目                 | 値                                                      |
| -------------------- | ------------------------------------------------------- |
| フックイベント名     | `PostToolUse`（唯一。`PreToolUse` / `Stop` 等は未定義） |
| matcher              | `Write\|Edit`                                           |
| コマンド文字列の全文 | `npx prettier --write . 2>/dev/null; true`              |

**`<REDACTED>` に置換した箇所は無い。** 秘密パターンの機械検査を掛けた結果、
`hooks` セクション内の一致はゼロだった。

```
$ grep -nEi '(api[_-]?key|secret|token|password|bearer|sk-|ghp_|eyJ)' ~/.claude/settings.json
109: "**Secrets management**: Supabase Vault (service_role-only access via ...

127: "Routine under this repo's own tree (docs/, src/, supabase/functions/, tests/) ...
```

一致した4件はいずれも `autoMode` 内の**説明文（散文）**であり、秘密の値ではない。
`hooks` セクションの外にあり、上の引用範囲には含まれない。

### 押さえるべき挙動（3点）

1. **`--write .` はリポジトリ全体が対象。** 編集したファイルだけではない。
   pnpm-lock.yaml / ja.ts / env-diff.md が無関係に書き換わっていたのは、全てこの1本が原因
2. **`2>/dev/null; true` で必ず成功扱いになる。** 失敗しても気づけない
3. **今回のセッションでは一度も発火していない。** 全編集を Bash（heredoc / node スクリプト）で
   行ったため。`git status --porcelain docs/checklists/env-diff.md` が空であることで実測確認済み

### Q8-c. このフックは Sentio に閉じない

**閉じない。全プロジェクトで同じ破壊を起こす。** 根拠は3つ。

1. **定義の置き場所が `~/.claude/settings.json`**（ユーザーのグローバル設定）である。
   プロジェクト側ではない。Sentio の `.claude/settings.json` には `PreToolUse` の3本
   （`block-env-read` / `block-prod-ref` / `check-secrets-patterns`）しか無く、
   `PostToolUse` は定義されていない
2. **コマンドが `prettier --write .` である。** `.` はそのとき作業しているディレクトリを
   指すので、対象は Sentio ではなく「そのプロジェクト」になる
3. **`.prettierignore` が無いプロジェクトでは無防備である。**
   Sentio では 2026-08-20 に `.prettierignore` を作って `pnpm-lock.yaml` を守ったが、
   これは Sentio のリポジトリ内にしか存在しない。他プロジェクトの lockfile・生成物・
   インデント依存の Markdown は、今も同じ経路で書き換わる

したがって案2（フック側の修正）は Sentio 以外にも波及する対処であり、
案1・案3（`.prettierignore`）は Sentio 内にしか効かない。
