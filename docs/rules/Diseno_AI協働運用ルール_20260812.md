# Diseno 開発運用ルール — AI協働の関門と自動化の設計（2026-08-12版）

Lauda スライス2の実運用で確立したルール。全サービス（Lauda / Lecto / Motus / Sentio / Recto / Ratio）の
Claude プロジェクト・Claude Code・Claude in Chrome に共通適用する。
新チャットにはこのファイルを添付（またはプロジェクトナレッジに登録）すれば運用が復元される。

---

## 1. 役割分担（実行と検収の分離・変更不可）

- **Claude（チャット）**: 設計判断・指示書作成・検収。実行者の申告を信用せず実在で照合する
- **Claude Code**: 実装・調査・CI監視。読み取り専用の本番調査（ログ閲覧・functions list・
  Playwright での画面実測）は自律実行可。適用系は CI 経由のみ
- **Claude in Chrome**: Dashboard 操作の代行（Resend / Vercel / Supabase / GCP 等）。
  指示には必ず URL・禁止事項（既存設定の削除変更禁止・追加のみ等）・成功の見え方を含める
- **人間（梶谷さん）**: 3つの関門のみ握る（§2）。それ以外は自動側に委任してよい

## 2. 人間が握る3つの関門（自動化しない）

1. **本番適用の合図**（「push可」）
2. **秘密・課金・外部アカウントに触る操作の承認**（GCP / Stripe / Resend / DNS 等）
3. **本番実測の最終確認**（リリース判定に関わる画面を人間の目で1回見る）

理由: 実行者（LLM）は「実在と異なる申告」を構造的に起こす（1日で4件の実績: 
env登録虚偽・E2E空洞化・接続不可の未実測申告・誤った原因確定）。
実行と検収の利害分離だけがこれを止める。統合・全自動化はこの分離を壊すため禁止。

## 3. 検収ルール（Claude が毎回適用）

- **実在検収**: 登録・変更・デプロイの完了判定は、コマンド出力や報告文ではなく
  Dashboard 画面・受信箱の実物・SQL 実測値・ネットワークレスポンスで行う
- **CI緑の中身を見る**: テストを承認条件にした場合、CI ログで実行実態
  （skip の有無・実行時間・接続先）まで確認して合格とする
- **デプロイ完了後に検証**: 本番検証は CI のデプロイジョブ完了タイムスタンプを確認してから。
  送信済みメール等の不変物を「修正が反映されていない」と誤認しない
- **既知事実との突合**: 「証跡付きのもっともらしい結論」も、既知の世界
  （動作実績・過去の決定・同一プロジェクトの状態）と矛盾しないか照合してから採用する
- **指示には目的と環境を書く**: 「〜が動くように」ではなく「デプロイ前検証として、
  ローカル環境に対して」。空白は実装者の最も安易な解で埋まる
- **停止点の遵守**: plan mode → 承認 → 実装 → commit → 停止。承認前実装は原則差し戻し

## 4. Claude Code への常設指示（各リポジトリの CLAUDE.md に記載）

- **申告の禁止事項**: 試さずに「できない」と申告しない。実行せずに「完了」と報告しない。
  実測可能なことは実測し、実行結果の実物（レスポンス・ログ）を引用して報告する
- **CI監視の定型化**: push 後は CI 全ジョブの完了を自律監視し、完了時に
  「全ジョブ結果＋E2E の実行実態証跡（skip なし・実行時間・接続先）」を定型報告する。
  人間はこの間、離席してよい
- **一次自己検収**: 完了報告の前に §3 の基準で自己検収し、証跡（画面キャプチャ・
  ログ引用・実測値）を添えて報告する。証跡のない完了報告は再提出
- **人間作業のバッチ化**: 人間側の作業（Dashboard 操作等）が必要になったら、
  ブロッカーでない限り即依頼せず貯めて、パートの区切りでまとめて依頼する
- **貼り付け文の形式**: 「/」で始めない。秘密実値はチャット/コミット/ログ非経由
  （一時ファイル方式の場合は「全登録先の実在確認後に削除」の順を守る）
- **検証プロセスの後始末**: 検証用に起動したプロセスは終了前に停止する

## 5. 環境差分チェックリスト（新環境・新スキーマ・新サービス着手時に必ず点検）

ローカルで動いても本番で動かない障害の型。1日で2件発生した実績
（PGRST106: v2 スキーマ非公開 / Vault: 関数実装がローカルのみ通る）。

- [ ] **Exposed schemas**: 新スキーマは Supabase Dashboard の API Settings に登録したか
      （未登録は PGRST106 が「静かな空状態」として現れる）
- [ ] **Extensions**: 本番プロジェクトで必要拡張が有効か（ローカル supabase start の
      自動有効化に騙されない）
- [ ] **env / Secrets**: Vercel env と Supabase Function Secrets の両方に、最新値が
      入っているか（Updated 日時で照合。登録先プロジェクトの取り違えに注意）
- [ ] **DNS / ドメイン認証**: ネームサーバー切替をまたいだドメインは Resend 等の
      認証が Failed に転落していないか（メール疎通で検知できる）
- [ ] **RLS**: 新テーブルへの書き込み経路には INSERT/UPDATE ポリシーが実在するか
      （不在は「静かな0件」として現れる。保存 API はエラー時に必ずユーザーに失敗を表示）
- [ ] **redirect URI**: OAuth は本番 URL＋localhost の2本。プレビュー環境では検証不可を前提化

## 6. UI・実装の共通原則（障害の可視化）

- **空状態とエラーを同じ見た目にしない**: 読み取り失敗時は「読み込みに失敗しました」、
  0件時は空状態文言。区別がないと障害が「静かな空」として隠れる
- **ユーザー向けエラー文言に内部コード（RLS_VIOLATION 等）を出さない**: 
  詳細は console.error と URL パラメータで開発者が取れれば足りる
- **実行不能な案内を出さない**: 「〜を登録してください」と案内するなら、
  その登録手段が同じ画面に実在すること
- **i18n 辞書経由**: 文言のハードコード禁止（ブランド固有名詞は例外）

## 7. 待ち時間の設計

- **CI待ち（5〜15分）は放置してよい待ちに変える**: §4 の定型監視・定型報告により、
  人間は報告が出たときだけ戻る
- **別プロジェクトの並行作業は自由**: 各サービスの文脈は引き継ぎ書と PROGRESS.md に
  固定されているため、待ち時間に他サービスの検討を挟んでも壊れない
- **伝書鳩の圧縮**: 定型の検収→承認→続行は CLAUDE.md の一次自己検収で圧縮し、
  人間を経由するのは判断が要る点のみにする

## 8. 障害対応の型

- **切り分けは段階番号で**: 実測手順に段階番号を振り、失敗報告は「段階＋画面＋エラー文言の
  実物」で受ける。段階と原因系の対応表を事前に用意する
- **原因確定の条件**: 「旧が失敗し新が成功する」の対で因果を閉じる。新が動くだけでは
  別因子の隠蔽リスクが残る
- **誤りの記録**: 誤った原因確定・虚偽申告は PROGRESS.md に記録し、同型の再発を
  チェックリスト化する。帰責は「虚偽の発生は実行者・本番到達は検収者」で整理する

## 9. 言葉遣い・表記（全サービス共通）

- 「死ぬ」等の表現禁止 → 「失効」「無効」「停止」
- Lauda のロゴ表記はコード・ウィジェット・指示書で "L"+"a"(#C8A090)+"uda"
  （フッター等のプレーンテキストは対象外）
- UI に AI 用語・API 技術用語を出さない（「Google連携」等の平易な表現）
