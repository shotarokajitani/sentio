# S-3-4 `state-narratives` の位置づけと記銘3経路の整合

契約 `docs/contracts/slice-state-repair.md` の **S-3-4**。
「`state-narratives` が『パイプラインの1段』ではないことを踏まえた構成になっている。
夜間の記銘経路は `baselines` 再計算と `summary` 再生成の2本とし、narratives の upsert は
イベント駆動（dialogue 発生時）に位置づける。**この整理が `docs/spec/02_state.md` の
記銘3経路と矛盾しないことを文書で示す**」に対する回答。

---

## 1. 構成はこのスライスで新たに決めたものではない

着手時に「構成の判断が要る」と見立てたが、**実測すると既に確定していた**。

| 出所                                               | 記述                                                                                                                                                                                |
| -------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 契約 P-2（`slice-state-repair.md:104-109`）        | 「**1件の narrative を upsert する単発APIであり、`company_id` だけを渡して呼べない**。`state-baselines → state-narratives → state-summary` を一列に並べる cron 設計は成り立たない」 |
| `supabase/functions/state-narratives/index.ts:3-7` | 「**これは「夜間バッチの1段」ではない**（契約 P-2 / S-3-4）… 夜間の記銘経路は baselines 再計算と summary 再生成の2本にする」                                                        |

したがって S-3-4 の未了部分は**構成の選択ではなく、整合を文書で示すこと**である。

## 2. 仕様の3経路との突合

`docs/spec/02_state.md:24-26` の記銘の規律:

> (a) baselines夜間再計算（決定的） (b) narratives upsert（confidenceルール付き） (c) summary再生成（章立て・上限で拘束）

契約 S-3-4 の整理と並べる。

| 経路                  | 仕様の記述                   | 起動のきっかけ                   | 契約 S-3-4 の整理               | 矛盾                                                   |
| --------------------- | ---------------------------- | -------------------------------- | ------------------------------- | ------------------------------------------------------ |
| (a) baselines 再計算  | 「**夜間**再計算（決定的）」 | 夜間 cron                        | 夜間の2本のうち1本              | **無し**（仕様が明示的に夜間と書いている）             |
| (b) narratives upsert | 「confidenceルール付き」     | **仕様は起動契機を書いていない** | イベント駆動（dialogue 発生時） | **無し**（後述）                                       |
| (c) summary 再生成    | 「章立て・上限で拘束」       | 記載なし                         | 夜間の2本のうち1本              | **無し**（拘束条件のみの記述で、契機を排除していない） |

**要点は (b) である。** 仕様が「夜間」と明記しているのは (a) だけで、
(b) には起動契機の指定が無い。仕様が定めているのは
「**記銘は3経路のみ・自由文追記禁止**」という**入口の数**の規律であって、
3経路すべてが同じスケジュールで走ることではない。

したがって「(a)(c) は夜間、(b) はイベント駆動」という整理は、
**仕様の3経路を1本も増やしていないし、減らしてもいない。** 矛盾しない。

### なぜ (b) だけ夜間に載らないか

(a) と (c) は `company_id` だけを渡せば起動できる。
「その会社について、いま持っている材料で計算し直す」ことに意味があるからである。

(b) は違う。`state-narratives` は `category` / `topic` / `content` / `source_event_ids` を
**呼び出し元が決めて渡す**。夜間に `company_id` だけで叩いても、
何を記銘すべきかがどこにも無い。**入力が足りないので、そもそも呼べない。**
これが「パイプラインの1段ではない」の実体である。

## 3. 現在の実装状態（実測）

```
$ grep -rn '"dialogue"' supabase/functions/ src/ --include="*.ts" | grep -v test
（0件）

$ grep -rn "state-narratives" supabase/functions/ src/ --include="*.ts"
supabase/functions/state-narratives/index.ts の自己言及のみ
（本番コードからの呼び出しは0件）
```

- **`event_type: "dialogue"` を扱う本番コードは無い**
- **`state-narratives` を呼ぶ本番コードは無い**（`tests/integration/edge-functions.test.ts` が直接叩いているだけ）

これは欠陥ではなく、**dialogue の発生源（「Sentioに聞く」）がまだ無い**ことの帰結である。
S-3-4 が要求しているのは「イベント駆動に**位置づける**」ことであり、
呼び出し元の実装ではない。cron 登録（A-2）は契約で本スライスの後と決まっている
（「壊れたFunctionを cron に載せない」）。

## 4. 結論

- 夜間の記銘経路は **2本**（`state-baselines` / `state-summary`）
- `state-narratives` は**イベント駆動の単発API**。夜間 cron に載せない
- この整理は `docs/spec/02_state.md` の記銘3経路と**矛盾しない**。
  仕様は入口の数を縛っており、起動契機を3経路で揃えることは求めていない
- **(b) の呼び出し元は未実装。** dialogue の発生源が入る時点で接続する

## 5. 未判断（勝手に決めない）

**(b) の呼び出し元をどこに置くか**は、dialogue の発生源が決まってから確定させる。
現時点の候補は2つで、どちらも本スライスの範囲外。

1. **ingest 経路から呼ぶ** — `event_type: "dialogue"` を受けた時点で `state-narratives` を呼ぶ。
   契約の文言に忠実だが、ingest（取り込み層）が State 層を呼ぶ向きの依存が新しく生まれる
2. **記銘専用の呼び出し元を1本立てる** — ingest はイベントを流すだけにし、
   「何を記銘するか」の判断をそこに閉じる。依存の向きは綺麗だが Function が1本増え、
   デプロイ対象と CI のプローブ突合の期待値（現在18本）が変わる

`run-sense` の中に混ぜる案は**採らない**。契約 P-2 が排除している
（「パイプラインの1段ではない」と正面から衝突する）。
