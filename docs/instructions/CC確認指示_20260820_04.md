## 【3】判断(3) — Q4 照合スクリプトは**着手可**。`yaml` の追加も**可**

### 3-1. `yaml` を devDependency に入れてよい

条件は3つです。

1. **devDependency に限る。** 実行時バンドルに乗せないこと
2. スクリプト冒頭に「なぜこの依存が要るか」を書くこと。
   `package.json` にはコメントが書けないため、根拠の置き場所がそこしかありません
3. ADR の追記は不要です。検査器専用の devDependency はスタック変更に当たりません

参考までに、`js-yaml@4.3.1` は既に lockfile に居ます（推移依存）。
ただし pnpm の隔離レイアウトでは直接 import できず、直接依存に昇格させるなら
`@types/js-yaml` も要るため、**正味の追加数は `yaml` と同じ**です。
型定義を同梱している `yaml` の方が素直なので、あなたの提案どおりで構いません。

### 3-2. あなたの設計への同意点

- 宣言ファイル（`must_run_in`）を正とする方向に同意します。単純な集合包含では
  「`check:allowlist` が verify に載っていてはいけない」を表現できません（Q4-c）
- **陰性コントロールをユニットテストで持つ**（固定フィクスチャで forbidden / missing を
  返させる）は必須です。実物のワークフローだけを入力にすると、全部緑のとき
  検査器の故障が見えません。`check:allowlist` が1行 log で緑を返していた空洞と同型という
  あなたの読みは正確です
- 守れない範囲を `hooks-coverage.md` と同じ形で文書に明記する方針にも同意します

### 3-3. あなたが「残る穴」と書いた範囲は、もう一段狭められます

あなたは「宣言ファイルの `must_run_in` に検査器を書き忘れた場合は捕まらない」と書きました。
**その一部は機械で捕まえられます。**

`package.json` の `scripts` にある `check:*` を左辺、宣言ファイルのエントリを右辺として
**両方向の集合差**を取ってください。

- 左にあって右に無い → **宣言への書き忘れ**（捕まる）
- 右にあって左に無い → 宣言が実在しない検査器を指している（捕まる）

これで残る穴は「**`package.json` の `scripts` に登録せずに検査器を作った**」場合だけになります。
`hooks-coverage.md` 形式で明記するのは、この狭めた後の範囲にしてください。
「宣言の網羅性は丸ごと人間の責任」と書くと、実際より広く諦めたことになります。

### 3-4. Q4-d への回答

照合スクリプト自身は `ci.yml` の `verify` ジョブに載せてください（実DB不要のため）。
