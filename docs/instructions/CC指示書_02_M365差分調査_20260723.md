# Claude Code 指示書 #02 — Microsoft 365 コネクタ 差分調査（read-only）

## 種別

**調査のみ。コードは1行も書かない。**

成果物は調査レポート1本。次セッションでこのレポートを入力として、M365コネクタのスライス契約を作成する。

## 目的

Sentio の現行コネクタは Google カレンダーのみである。ターゲット層（税理士チャネル経由の製造・建設・小売）は Outlook 予定表を使っている割合が高いと想定され、このままでは該当層のカレンダーデータを一切取得できない。

Microsoft Graph API による Outlook 予定表コネクタを実装するために、**既存の Google カレンダー実装から何がそのまま使えて、何を作り直す必要があるか**を確定させる。

## 調査手順

### Step 1. 既存実装の棚卸し

以下を読み、Google カレンダー連携の全経路を構造として書き出す。

- OAuth 開始・コールバック処理（`google-calendar-oauth` 相当）
- トークンの保存先と暗号化方式（Supabase Vault の使用箇所・K1〜K4区分のどれか）
- トークンリフレッシュの実装箇所とタイミング
- データ同期処理（`sync-*` 系）
- 取得したイベントを Ingest エンベロープに変換する箇所
- エンベロープの sensitivity 区分（S0〜S3）のどれを付与しているか
- 冪等性の担保方法（重複取り込みの防止キー）
- エラー処理・リトライ・失敗時のユーザー通知
- フロントエンドの連携ボタン・接続状態表示

各項目について、**ファイルパスと関数名を必ず併記**すること。

### Step 2. 抽象化可能性の判定

Step 1 の各要素について、以下の3分類で判定する。

| 分類 | 意味 |
|---|---|
| `shared` | プロバイダ非依存。そのまま共通利用できる |
| `parameterized` | 構造は同じ。エンドポイント・スコープ等の差し替えで対応できる |
| `provider_specific` | Microsoft 用に作り直しが必要 |

判定結果を一覧表にする。`provider_specific` については理由を1行で書く。

### Step 3. Microsoft Graph 側の要件整理

以下を公式ドキュメントで確認し、Google 側との対比表にまとめる。ドキュメントのURLを必ず併記すること。

| 確認項目 | 内容 |
|---|---|
| アプリ登録 | Azure AD（Microsoft Entra ID）でのアプリ登録に必要な設定項目 |
| 認証方式 | 認可コードフロー／PKCE の要否。Google 実装との差異 |
| スコープ | 予定表読み取りに必要な最小スコープ。委任アクセスとアプリケーションアクセスの違い |
| 管理者同意 | 管理者同意が必要になる条件。テナント管理者不在の中小企業で通るか |
| トークン | アクセストークン・リフレッシュトークンの有効期限、更新方式 |
| エンドポイント | 予定表イベント取得のエンドポイントとページング方式 |
| 差分取得 | デルタクエリの有無と、遡及バックフィルへの適用可否 |
| レート制限 | スロットリングの閾値と、429 応答時の推奨挙動 |
| マルチテナント | シングルテナント／マルチテナントアプリの選択が必要か |
| 審査 | Google カレンダーのような公開審査プロセスに相当するものがあるか、所要期間 |

### Step 4. リスクの洗い出し

以下の観点で、実装前に潰すべきリスクを列挙する。

- 管理者同意が必要な場合、5〜50名規模の会社で「誰が承認するのか」が詰まる可能性
- Microsoft 365 のプラン差（Business Basic / Standard / Premium）による API 利用可否の違い
- Exchange Online を契約していない M365 構成が存在するか
- Google 側と Microsoft 側で取得できるイベント属性が異なることによる、Sense 層への影響
- 既存の `integrations` テーブル等のスキーマが、複数プロバイダのカレンダーを保持できる構造になっているか（**なっていない場合、必要なスキーマ変更を提案として書く。実行はしない**）
