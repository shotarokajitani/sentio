## 目的

`/privacy` §6 は2つの経路を並記している。

> お客様が **Sentio の画面** または **Google アカウントの設定** から Google との連携を
> 解除した場合、アクセストークン・リフレッシュトークンを直ちに破棄します／
> 当該連携から取得した Google ユーザーデータを30日以内に削除します。

`src/app/api/connections/disconnect/route.ts` はこの約束の実体だが、
**どちらの経路からも到達しない。** 案A はこの2経路を両方とも実装する。

**書いた時点で守る義務が発生する。** 再提出時点で本番に出ている `/privacy` が
約束の正本になるため、このスライスが閉じるまで再提出してはならない。

## 起草者の推奨（**承認が要る決定**）

| #       | 論点                                   | 推奨                               | 理由                                                                                                                                     |
| ------- | -------------------------------------- | ---------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------- |
| **D-1** | 画面の解除に猶予期間を置くか           | **置かない（即時削除のまま）**     | P-1 の既存挙動を変えずに済む。「30日以内」は 0日でも満たす。遅らせる仕掛けは消し忘れの余地を作る（API のコメントも同じ理由を書いている） |
| **D-2** | 画面の解除に二段確認を置くか           | **置く。会社名の入力を求める**     | 削除は取り返しがつかない。誤操作1回でイベントが消える形は作らない                                                                        |
| **D-3** | `invalid_grant` を即座に解除とみなすか | **みなさない。30日待つ**           | `invalid_grant` は取り消し以外（トークン期限切れ・6ヶ月無操作・パスワード変更）でも返る。**断定はできない**                              |
| **D-4** | 30日の起点をどこに持つか               | `connections.revoked_at`（新規列） | P-6 のとおり既存列では表現できない。`last_refresh` の流用は意味が二重になる                                                              |
| **D-5** | 削除の実行者                           | `retention-purge` に相乗り         | 既に日次で回る。門（件数チェック / `company_id` 必須）を二重に持たない                                                                   |

**D-3 の代償を明示する。** 30日待つ間、お客様が Google 側で取り消した後も
Sentio 側にデータが残る。§6 は「30日以内に削除」と約束しているので**約束は守れる**が、
「直ちに」ではない。トークンの破棄は検知した時点で直ちに行う（下記 D-2-2）。

#### 同じ実測で見つかった別の不具合（**D 系の基準外。未修正**）

`/connect` は本番で **React error #418（hydration mismatch）** を投げている。

```
Error: Minified React error #418; visit https://react.dev/errors/418?args[]=text&args[]=
```

原因は `src/app/connect/connect-client.tsx:117-124` の `formatDate`。

```ts
return new Date(iso).toLocaleString("ja-JP", { month:"short", day:"numeric", hour:"2-digit", minute:"2-digit" });
```

**`timeZone` を指定していない。** サーバ（Vercel＝UTC）は `8月22日 17:18` を描き、
クライアント（JST）は `8月23日 02:18` を描く。差はちょうど9時間で、これが不一致になる。

- **解除ボタンの動作には影響していない。** React が再描画で回復しており、
  ボタンは実際に押せて二段確認も開く（上記）
- ただし**表示が一瞬 UTC で出てから JST に飛ぶ**。「最終同期」がずれて見える
- 修正は `timeZone: "Asia/Tokyo"` の明示。**このスライスの範囲外なので、ここでは直していない**

## 実装順

1. **D-2（判別）を先に入れる。** 削除を足す前に、`revoked` と `reauth_required` が
   正しく分かれることを実データで見る。ここが誤っていると D-3 が誤削除装置になる
2. **D-1（画面）** — 既存 API を呼ぶだけなので、判別と独立に入る
3. **D-3（30日削除）は最後。** D-2 の判別精度を本番の実績で確かめてから入れる

> **2 と 3 の間に本番実績を見る停止点を置く。** `revoked` が立った実例を1件以上観測し、
> それが本当に取り消しだったかを人間が確認するまで、D-3 を有効にしない。
> 検知が壊れたまま自動削除を入れると、**気づいたときには消えている。**

### U-2 の確定内容（2026-08-27）

**解除の二段確認は、ログイン中のアカウントのメールアドレスを入力させる。**
照合は**前後の空白を落とし、大文字小文字を無視して**比較する。
**一致しない限り API を呼ばない**（受入基準 D-1-2 の陰性コントロールはここを見る）。

**会社名を採らなかった理由: 会社名の正本がデータベースに存在しないため。**
2026-08-27 に実測した事実は次のとおり。

| 事実                                                                        | 出典                                                   |
| --------------------------------------------------------------------------- | ------------------------------------------------------ |
| サインアップは `signUp({ email, password })` のみ。会社名を受け取っていない | `src/app/api/auth/session/route.ts:37`                 |
| 会社の同一性は `auth.users.id` が担う（RLS は `company_id = auth.uid()`）   | `src/lib/auth/company.ts:6` / `00019`                  |
| `company_summary` にも会社名の列は無い                                      | `supabase/migrations/00005_create_company_summary.sql` |
