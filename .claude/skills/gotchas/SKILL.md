- デプロイ順序とfail-open禁止: migrationsを先・functionsを後にする（`needs: [verify, deploy-migrations]`）。逆順や並列だと「関数はデプロイ済みだがそれが呼ぶDB関数が未適用」の不整合が残る（00017未適用のままsync-connectionsが本番に出た事故・2026-08-12）。またfunctionを個別stepに分ける際、`|| true`や`continue-on-error: true`でエラーを吸収してはいけない（Slice 1欠陥#6/#7と同型のfail-open）。`if: ${{ !cancelled() }}`なら後続stepを実行しつつ失敗はジョブ失敗として顕在化する
- migration履歴のドリフト（旧プロジェクト由来）: `supabase db push`は「remoteに適用済みだがlocalに無いバージョン」を検出すると`Remote migration versions not found in local migrations directory.`で中断する。Sentioの本番には**アーカイブ済み旧プロジェクトの履歴2件（20260414183617 / 20260414183945）が残っており**、`archive/legacy`ブランチの`supabase/migrations/20260414_*.sql`が出所。同じSupabaseプロジェクトを作り直さずにスキーマを刷新した場合に必ず起きる。**修復（`migration repair`）の前に本番の実スキーマを必ず診断すること**（`docs/runbooks/2026-08-12_migration-state-diagnosis.md`）。履歴だけ直すと、旧テーブル残存時に`00013_enable_rls_all.sql`のRLSアサーションが`RAISE EXCEPTION`で発火し、00001〜00012がコミット済みの**部分適用状態**で止まる。さらに`00014`の`GRANT ... ON ALL TABLES IN SCHEMA public`が旧テーブルにも`anon` SELECTを付与する（deploy #31576330545・2026-08-12）
- Dashboard SQL Editorでの適用は履歴に残らない: `supabase_migrations.schema_migrations`に記録されるのはCLI/CI経由の`db push`のみ。Dashboardで流したDDLは記録されないため、「履歴に無い＝スキーマにも無い」は成り立たない。本番状態の判断は履歴ではなく**実オブジェクトの存在確認**で行うこと
- マイグレーションの再実行安全性: `00015_alter_delivery_log_union_schema.sql`は`UPDATE delivery_log SET delivery_type = frame`の後に`DROP COLUMN IF EXISTS frame`を実行するため、**2回目は`column "frame" does not exist`で失敗する**。他の00001〜00018は`IF NOT EXISTS` / `DO $$ EXCEPTION WHEN duplicate_object` / `CREATE OR REPLACE` / `cron.schedule`上書きで再実行安全。列を参照するDML行は必ず列存在ガードで包むこと
- hooksの相対パス自爆: `.claude/settings.json`のhookコマンドを`node .claude/hooks/x.mjs`と相対指定すると、セッションのcwdがサブディレクトリに移った瞬間に`MODULE_NOT_FOUND`となり、hookがfail-closedで**Bash/Read/Edit/Writeを全てdenyしてセッションが自縄自縛になる**（`cd supabase/migrations`で実際に発生）。自力で復旧できないのは、設定を直すためのEdit自体がブロックされるため。必ず`node "$CLAUDE_PROJECT_DIR/.claude/hooks/x.mjs"`と絶対指定すること（2026-08-12）
- default privilegesは自前のALTER DEFAULT PRIVILEGESを消しても無くならない: Supabaseホスト環境はプロジェクト初期化時に`anon`/`authenticated`/`service_role`向けのデフォルト権限を**プラットフォーム側で**設定している。マイグレーションから自前の`ALTER DEFAULT PRIVILEGES`を削除しても、`public`に新規作成したテーブルには**ビルトインのデフォルト権限が付く**。したがって「権限は明示しないと付かない＝fail-closed」は**ローカル(supabase start)でしか成立しない**。新テーブルの安全の本線はGRANT側ではなく、**CLAUDE.md絶対規則「全テーブルRLS必須」**（RLS有効かつポリシー未定義なら非superuserから全拒否＝fail-closed）である。`00013`のRLS検証リストへの追記漏れは、GRANTの追記漏れと違って**エラーにならず静かに全公開になる**ため、新テーブル追加時は00013への追記を最優先で確認すること（2026-08-15）
- skipされ続けるテストは腐る: `tests/integration/ingest-calendar.test.ts`の「全てのoccurred_atが過去である」は、CIにSUPABASE_*が無くskipされ続けた結果、**毎月1〜14日には必ず落ちる状態**で放置されていた（フィクスチャが`monthsAgo=0`＝当月15日を含むため未来日になる。CI実行日2026-08-14 UTCで約17時間先の日付を生成）。skipは「pass」ではなく「未検証」であり、緑のCIが実態を保証しない。統合テストをskip可能にするなら、**skipされている事実と件数を必ず可視化**すること。日付フィクスチャは月末日への`setMonth`桁溢れも起こすため、日を固定してから月を引く（2026-08-15）
- workflow YAMLの無引用スカラー: ステップ名やジョブ名に`": "`（コロン+空白）を含めると、YAMLがマッピングとして解釈し**ワークフロー全体が構文エラーで1ジョブも起動しない**（`- name: deno check (npm: 指定子の解決...)`で発生。GitHubは「This run likely failed because of a workflow file issue」としか出さず、`gh run view`にもジョブが一切現れないため原因が読めない）。`npm:` `npm:@scope/pkg` 等を名前に書くときは必ず引用符で囲む。push前に`node -e "require('js-yaml').load(require('fs').readFileSync('.github/workflows/ci.yml','utf8'))"`でパースを通すこと（2026-08-15）
- 人間依頼のバックアップは申告でなく実物で検収する: 旧スキーマ16テーブルのDROP（00021）前に「JSONスナップショット取得済み」の申告を受けて破壊的操作に進んだが、**保存時の取り違えで実際には取得されておらず、削除後に材料喪失が判明した**（今回は旧DBの実データがテスト会社1件のみ＝実ユーザーゼロだったため実害なしで済んだ）。実行と検収の分離は自分の作業だけでなく**人間側の前提作業にも適用する**: バックアップ・エクスポート・設定変更などを前提に破壊的操作へ進む前は、「完了しました」の申告ではなく**ファイル冒頭・行数・対象テーブル名などの実物**を1回確認してから進むこと。取り返しがつかない操作ほど、前提の検収を省略しない（2026-08-18）
- パイプで終了コードが化ける: `pnpm test 2>&1 | tail -4` のようにパイプを挟むと、`$?` は**パイプ最後のコマンド（tail）のもの**になるため常に0になる。`cmd && git commit` の形にしていても、テストが赤いまま素通りしてコミット・pushまで到達する（実際に2件failのまま push した・2026-08-17）。検証コマンドは**パイプせずに実行して `echo $?` で明示確認**するか、出力が要るなら `cmd > /tmp/out 2>&1; echo $?` のようにリダイレクトして終了コードを分離する。`set -o pipefail` でも可だが、Bashツールは毎回新しいシェルなので都度指定が要る点に注意（2026-08-17）
- 正規表現の `.` は `\r` にマッチしない: JavaScriptの `.` は行終端子（`\n` `\r`）を除く任意文字。`text.split("\n").map(l => l.replace(/--.*$/, ""))` のような行末処理は、**CRLFのファイルでは1つもマッチせず完全に空振り**する（`.*` が `\r` を消費できず `$` に到達しないため）。このリポジトリは `core.autocrlf` が有効で、**LFで書いた直後は通るのに、`git restore` や rebase で作業ツリーがCRLFに変換された後で初めて壊れる**という再現しにくい形で出た（`executableSql` が SQLコメントを除去できずテスト2件fail・2026-08-17）。行末処理は `[^\n]` を使い、**LF/CRLF両方を実測**してから確定させること（2026-08-17）
- リモート実物検証: ローカルで修正→テストPASS→コミット・プッシュしても、リモートの実物が意図通りとは限らない。コミット時にgit addが漏れている・.gitattributes等でファイルが変換される等の原因がある。push後は`git show origin/branch:path`でリモート実物を引用確認すること。「ローカルPASS」の申告とリモート実物の乖離はVercel Preview等のCI失敗として顕在化する（2026-08-12）
- グローバルhookがlockfileを書き換える: `~/.claude/settings.json` の PostToolUse に `npx prettier --write .` があると、**Write/Edit のたびにリポジトリ全体が整形され `pnpm-lock.yaml` が3000行規模で書き換わる**。commitの`git status`まで気づかず、CIの`pnpm install --frozen-lockfile`を壊しかねない（2026-08-18に実際にコミットへ混入し、`git checkout HEAD -- pnpm-lock.yaml`＋amendで除去）。commit直前に`git status`でlockfileが変更対象に入っていないかを毎回確認すること。恒久対策は`.prettierignore`に`pnpm-lock.yaml`を入れるか、hookの対象をステージ済みファイルに絞ること（未実施・要判断）
- hookの`EUNKNOWN (uv_spawn)`はhookの故障ではない: Stop hookが`EUNKNOWN (uv_spawn)`で落ちた原因は、**マシンのコミットチャージ枯渇でプロセスを生成できなかったこと**だった（物理7.8GB/空き0.6GB、コミット上限22.5GBに対し空き0.8GB。Chrome47プロセス7.7GB＋Claude13プロセス3.7GB）。libuvはCreateProcess失敗をEUNKNOWNで返す。同じ状況では`node .claude/hooks/*.mjs`も`VirtualAlloc failed`／`fork: Resource temporarily unavailable`で落ちる。**hooksを疑う前にメモリを見る**（`Get-CimInstance Win32_OperatingSystem`のFreeVirtualMemory）。余裕があれば同じhookはexit=0で通る。selftestは20/20 passでスクリプト論理は健全だった（2026-08-18）
- `check:allowlist` はCIで空洞のまま緑を返す: `pnpm run check:allowlist` のCLI入口（`scripts/check-allowlist.ts` 末尾の `import.meta.url === file://${process.argv[1]}` ブロック）は **`console.log("check:allowlist — run against live DB")` を1行出すだけで、実DBのカラムを一切照会していない**。純粋関数 `validateS2Columns` は `tests/unit/allowlist.test.ts` の3ケースで検証されているが、**CIジョブ `verify` のこのstepは実スキーマに何が起きていても必ずexit 0になる**（run 32134357004 の実ログでも出力はこの1行のみ）。CLAUDE.md絶対規則「S2テーブルに本文型カラムを追加しない」の機械的担保は、現状**存在しない**。「skipされ続けるテストは腐る」と同型だが、skip表示すら出ない分こちらの方が読めない。ステップ名やscript名が検査を示唆していても、**実ログの出力行数で実施を確認する**こと（2026-08-18）
- `next dev` が `CLAUDE.md` を書き換える: Next.jsは既定 `agentRules: true` で、`next dev` 実行のたびに `CLAUDE.md` / `AGENTS.md` 末尾へ `<!-- BEGIN:nextjs-agent-rules -->` ブロックを自動追記する（実装 `node_modules/next/dist/server/lib/generate-agent-files.js`、定義 `node_modules/next/dist/server/config-shared.d.ts` の `agentRules?: boolean`）。ブロック自身が「差分から消しても再生成されるので一緒にコミットしろ」と書いているが、**CLAUDE.mdはプロジェクト憲法＝人間承認事項なのでツール追記を受け入れてはならない**。`next.config.ts` に `agentRules: false` を設定して封じる。検証のためdev serverを起動したら、commit前に `git status` でCLAUDE.mdが変更対象に入っていないか必ず見る（2026-08-18）
- `vault.secrets` は UPDATE 不可・DELETE 可という非対称: `00022` の実測どおり `vault.secrets` への直接 UPDATE は SECURITY DEFINER でも `permission denied for table secrets` に落ちるが、**DELETE は postgres ロールでそのまま通る**（2026-08-18・本番切替時に、ロールバックで終わるプローブで実測）。「UPDATE が拒否されたのだから DELETE も拒否されるはず」は成り立たない。逆に「DELETE が通るのだから UPDATE も通るはず」も成り立たない。**Vault のテーブル権限は操作ごとに違うので、操作ごとに実測する**。値の更新は `vault.update_secret()` 経由が必須で、削除は直接 DELETE でよい。この非対称のため `delete_vault_secret` の security definer 関数は不要と判断した（作っていない）。破壊的SQLの前に権限を確かめるときは、`begin; … rollback;` で囲んだプローブを使えば実物を壊さずに済む（2026-08-18）
- `connections` に `created_at` は無い: 列は `id` / `company_id` / `provider` / `vault_secret_id` / `scopes` / `status` / `last_refresh` / `expires_at` の8つだけ（`00007`）。手順書に `select ... created_at from connections` と書いてしまい、本番の SQL Editor で `column "created_at" does not exist` として顕在化した（2026-08-18）。時系列で並べるなら `last_refresh`。**手順書に載せるSQLは、書いた時点でマイグレーションの列定義と突き合わせること。** 実行者が人間で、実行先が本番の場合、間違いはレビューではなく本番のエラーで発見される

- SQL文字列中の `'\t'` はタブにならない: JS側で `"SELECT a || '\\t' || b ..."` と書くと、SQLに届く文字列リテラルは `'\t'`、すなわち**タブ1文字ではなくバックスラッシュ + t の2文字**になる（`standard_conforming_strings = on` が既定で、SQLの通常文字列リテラルはC言語風エスケープを解釈しない。解釈させたいなら `E'\t'`）。JS側の `split("\t")` と噛み合わず、**全行が1カラムとして読まれて2列目が `undefined` になる**。2026-08-19 の `scripts/live-schema.ts` で実際に起き、`check:schema` が **259件すべてを「存在しない列」と誤判定**した。区切りはSQL文字列に埋め込まず **`psql -A -t -F "\t" -c ...`** で渡す（`-F` が区切り、`-A` が非整列、`-t` がヘッダ抑止。`-At` と `-F` は併用できる）。症状の出方が重要で、**「検査が通らない」ではなく「検査が全部落ちる」形**で出る。全件が同じ理由で落ちたら、対象ではなく**検査側の入出力形式**をまず疑う（2026-08-19）
