## 目的

push 4枠（パルス／即時／週次／月次）は「Sentioが選んだものが届く」体験である。
これに対し **pull は「経営者が聞きたいときに聞ける」唯一の枠**であり、
`docs/spec/00_overview.md` §6 で「無制限・証拠遡及可」と定義されている。

本契約のゴールは、**経営者の自然文の問いに対して、自社の会社モデル（State層）だけを根拠に答え、
その答えの全ての事実が証拠イベントに遡れる**状態を1本通すこと。
新しい検索系・新しい記憶を作らない。`docs/spec/02_state.md` の
「Investigator・『Sentioに聞く』・週次生成は同一編成器経由」を実装で守る。

## スコープ / 非スコープ

IN:

- Web（ログイン済み画面）からの質問→回答の1往復
- 記憶パケット編成器（`state-memory-packet`）の**使い回し**と、pull用途に必要な最小限の拡張
- 回答本文への**証拠参照の付与**（イベント／Findingへの遡及）
- 未接続領域に対する定型応答（「そこはまだ見えていません」）
- 質問と回答の `dialogue` イベント化と narratives への還流
- pull のコスト統制（下記 Q-5）

OUT（**今回作らない**。作りたくなったら契約を書き直す）:

## 前提として確定している制約（2026-08-19 実測。変えるなら本契約の外）

これらは推測ではなく、コードとマイグレーションの突き合わせで確認した事実である。
**契約の受入基準は、この現実の上に載る。**

### P-1 編成器は現在3セクション中2セクションが静かに空になる

`supabase/functions/state-memory-packet/index.ts` は5セクション
（summary / baselines / recent_events / findings / narratives）を組む設計だが、

- baselines を `metric_key, is_established, median, iqr` で選ぶ。実列に `median` / `iqr` は無い
  （`00003_create_baselines.sql`）→ `42703` → エラーは握られ `(no baselines)` になる
- narratives を `updated_at` で並べる。実列は `last_confirmed_at`（`00004`）→ 同上 `(no narratives)`

**つまり現状の編成器は「summary＋直近20件＋open findings」しか返さない。**
「Sentioに聞く」は編成器を使い回す以上、**この修復が本契約の前提工程になる**（Q-1-1）。
同型の不一致は `state-baselines` / `state-narratives` にもあり、
`docs/runbooks/2026-08-19_pipeline-first-run.md` §0.1〜§0.2 で本番実測にかけている。
**A-1 の実測結果が出るまで、修復の形（Function側を直すか、マイグレーションを足すか）は確定させない。**

### P-2 会社モデルに入っている実データは現状ほぼ無い

本番 `company_id = 197f2c0e-…` の events は 15 件・すべて `schedule`。
baselines / narratives / findings は 0 件。
**「答えられない」が正常応答になる場面が大半を占める**という前提で受入基準を設計する（Q-6）。

### P-3 調査予算の上限は現在まったく効いていない

`supabase/functions/investigate/index.ts:238-242` は `budget_usage` から
`used, daily_limit` を選ぶが、実列は `full_runs / light_runs`（`00010`）。
エラーは無視され `budgetData = null` → `budgetExhausted` が falsy になり、
**予算超過で止まる経路が存在しない**。
「無制限」を謳う pull を、上限の壊れた基盤の上に乗せない（Q-5）。

### P-4 Evaluator は spec の6基準ではなく5基準で動いている

`docs/spec/03_sense.md` はハード6基準（像／証拠／棄却／トーン／行動／**カバレッジ**）と定義するが、
`prompts/evaluator_criteria.md` と `supabase/functions/_shared/prompts.ts:15-22` は**5基準**で、
**基準6「カバレッジ」が存在しない**。`docs/contracts/slice-01.md` の D3 も「5基準」と書いている。
pull に何を課すかを決める前に、この drift をどちらに寄せるかの判断が要る（Q-D2）。

### P-5 認証は「1認証ユーザー＝1社」で確定済み

`00019_rls_with_check.sql` の全ポリシーが `company_id = auth.uid()`。
`src/lib/auth/company.ts` の `getAuthedContext()` がセッションから company_id を導出する。
**company_id をクエリ・ボディで受け取る経路は作らない**（スライスA A-2-2 で確定した規律）。

### P-6 Edge Function は全て `--no-verify-jwt` でデプロイされている

`.github/workflows/deploy.yml:82-160`。関数本文の `company_id` をそのまま service_role で扱うため、
**関数URLを知る第三者が任意の company_id を指定できる**。
「Sentioに聞く」を Edge Function として素直に実装すると、この穴の上に会話機能を載せることになる（Q-4-2）。

## 検収者の判断が要る点（**勝手に確定させない**）

| ID       | 論点                                                                              | 起草者の推奨                                                                                                                                    |
| -------- | --------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------- |
| **Q-D1** | pull の回答に **Evaluator を掛けるか**。掛けるなら push と同じ基準か、緩めるか    | **掛ける。ただし基準を差し替える**（下記「Q-D1 の判断材料」）                                                                                   |
| **Q-D2** | Evaluator の 5基準 / 6基準 drift（P-4）をどちらに寄せるか                         | spec 側（6基準）に寄せる。pull はカバレッジ基準が最も効く枠なので、ここで揃えるのが自然                                                         |
| **Q-D3** | 「無制限」の実装上の意味。回数無制限か、**深さ**が有限か                          | 回数は無制限、**深さ（＝Investigator起動）は0**。pull は編成器＋1回生成に固定する                                                               |
| **Q-D4** | 実装場所を Next.js の Route Handler（`/api/ask`）にするか、Edge Function にするか | **Route Handler**。`getAuthedContext()` がそのまま使え、P-6 の穴を踏まない                                                                      |
| **Q-D5** | 質問文・回答文の保存先と sensitivity                                              | `events` に `event_type='dialogue'` / `sensitivity='S3'`（`spec/01`「S3 本人対話（本文可。由来は本人発話のみ）」に合致）。本文は metrics に置く |

### Q-D1 の判断材料（Evaluatorを掛けるか）

**掛けない場合の主張**: pull は経営者が自分の意思で聞いた1往復であり、割り込んでいない。
push は「読まされる」ので品質の責任が重いが、pull は外れても経営者が聞き直せる。
Evaluator を挟むとレイテンシが倍近くになり、「聞いてすぐ返る」体験を損なう。

**掛ける場合の主張**（起草者はこちらを推す）:

1. `spec/04`「『Sentioに聞く』」に **「回答内の事実は証拠イベント遡及可能（基準2を会話にも適用）」と明記**されている。
   基準2だけを名指ししているが、基準2は Evaluator の一部であって単体では存在しない
2. 禁じ手7「証拠なき断定をしない」は枠を問わない。pull だけ緩めると、
   **「Sentioは聞かれると断定する」**という最悪の抜け穴になる
3. 品質基準（ハード閾値）「読んだ経営者の頭に一枚の絵が浮かぶか」は製品全体の閾値であり、pull を除外していない

**推奨する折衷**: 基準を**そのまま流用せず、pull用に読み替える**。

| push（Finding）基準 | pull（回答）での扱い                                                             |
| ------------------- | -------------------------------------------------------------------------------- |
| 1 像                | **緩める**。問いが「先月の会議は何件？」なら一枚の絵は要らない。適用しない       |
| 2 証拠              | **そのまま必須**（spec/04 明記）。落ちたら返さない                               |
| 3 棄却              | **緩める**。因果を問われたときのみ適用                                           |
| 4 トーン            | **そのまま必須**。care_only・査定文脈の禁止は枠を問わない                        |
| 5 行動              | **適用しない**。pull は次の一手を要求されていない                                |
| 6 カバレッジ        | **そのまま必須**。むしろ pull の主戦場（P-2 の状況では大半がここで確度を下げる） |

＝ **pull は「証拠・トーン・カバレッジ」の3基準**。revise は 1 回まで（往復のレイテンシ制約）。
この3基準案の是非が Q-D1 の判断そのもの。

## 受け入れ基準（全passが必要）

### Q-1 想起（編成器の使い回し・新しい検索系を作らない）

- **Q-1-1** 編成器（`state-memory-packet`）が baselines と narratives を実際に返す
  （P-1 の不一致を解消する）。**空でないパケットを返すことを実クエリテストで固定する**
- **Q-1-2** 「Sentioに聞く」は編成器を経由してのみ会社データに触れる。
  回答生成経路から `events` / `baselines` / `narratives` / `findings` への**直接クエリを書かない**
  （grep で「編成器を通さないテーブル参照が0件」を機械的に確認できること）
- **Q-1-3** 同じ質問に対し、週次生成が使うのと**同一のパケット組成**が使われる
  （`spec/02`「想起の一元化で回答の食い違いを構造的に防ぐ」）
- **Q-1-4** パケットはトークン上限内。超過時は優先度順に切り詰められる（`slice-01` C3 の再確認）

### Q-2 証拠遡及（本契約の核）

- **Q-2-1** 回答は本文と**証拠参照リスト**の2部構成で返る。
  参照は `event_id` / `finding.id` / `narrative.id` のいずれかを指す**実在するID**である
- **Q-2-2** **回答本文中の全ての事実主張に、証拠参照が1つ以上紐づく。**
  紐づかない主張が1つでもある回答は**返さない**（表示しない。fail-closed）
- **Q-2-3** 参照IDが実在しない（ハルシネーション）場合、その回答は破棄される。
  **生成された参照IDを保存前にDBで実在確認する**こと。リンク切れゼロを実クエリテストで固定する
  （`slice-01` D5 の pull 版）
- **Q-2-4** 経営者が証拠参照をたどると、**その事実の出所（source・occurred_at・種別）が画面上で確認できる**。
  「遡及可能」がAPIレスポンス内の文字列で終わらず、UIで到達できること
- **Q-2-5** 一般知識・外部知識のみに基づく回答を返さない。
  会社データに根拠が無い問いには Q-6 の定型応答を返す

### Q-3 品質ゲート

> **Q-D1 承認後に確定。以下は推奨案（3基準）を採った場合の基準文。**

- **Q-3-1** 回答は「証拠・トーン・カバレッジ」の3基準で判定され、全通過のみ表示される
- **Q-3-2** 判定ログ（各基準の pass/fail と理由）が回答ごとに保存される
- **Q-3-3** revise は最大1回。1回で通らなければ**回答を返さず**、
  「うまく答えられませんでした」＋見えている範囲の提示にフォールバックする（黙って低品質を返さない）
- **Q-3-4** 陽性／陰性コントロールで判定器が機能することを示す:
  - 陽性: 実データと証拠IDを伴う回答 → 3基準 pass
  - 陰性: 証拠IDの無い一般論の回答 → **基準「証拠」で fail**（`scores` が `{}` でないこと）
- **Q-3-5** Evaluator に渡すのは**回答と証拠のみ**。生成器の推論過程を渡さない
  （`spec/03` Evaluator独立性3防護）

### Q-4 認証・RLS・越境不可

- **Q-4-1** `company_id` は**セッション由来**（`getAuthedContext()`）。
  クエリパラメータ／リクエストボディから受け取る経路を作らない（P-5・スライスA A-2-2）
- **Q-4-2** 未認証リクエストは 401。**Edge Function 直叩きで他社の回答を得られる経路を作らない**
  （P-6。Q-D4 で Route Handler を採る場合、Edge Function 側に pull 用の入口を増やさない）
- **Q-4-3** 2ユーザー2社を実際に作り、**他社 company_id を明示的に指定しても他社データが
  回答に混入しない**ことを実クエリテストで固定する（テストコードとして残す）
- **Q-4-4** 回答・証拠参照・保存された dialogue イベントのすべてが自社スコープに閉じる
- **Q-4-5** `care_only = true` のエンティティが、評価・査定の文脈で回答に現れない
  （従業員に関する問いに対しケア文脈の文型のみ。禁じ手3）

### Q-5 コスト統制（「無制限」の意味を実装で定義する）

「無制限」は**回数の話であって、1回あたりの深さの話ではない**。上限は3箇所で効かせる。

- **Q-5-1** 1回の質問で消費するLLM呼び出しは**上限が定数で固定**されている
  （推奨: 生成1回＋判定1回＋revise時に最大2回追加＝**4回まで**）。
  pull から Investigator（フルハーネス）を起動しない（Q-D3）
- **Q-5-2** 編成器のトークン予算が pull でも適用される。パケットは上限内（Q-1-4）
- **Q-5-3** **異常利用に対する防御が存在する**。同一 company_id からの短時間の連打に対し、
  レート制限または日次上限が効く。上限に当たったときの応答は**明示**する（黙って劣化させない）
- **Q-5-4** pull の消費が `budget_usage` に記録される。
  **P-3 の不一致（`used` / `daily_limit` が実在しない）を解消してから記録経路を作る。**
  「記録しているつもりで一切記録されていない」状態を再演しない
- **Q-5-5** 上限値そのもの（何回／何トークン）は**プラン設計（スライス5）で可変にできる形**で持つ。
  ただし本契約では**固定値1つ**で足りる。entitlement は作らない
- **Q-5-6** 禁じ手9に抵触しないこと。**証拠遡及・カバレッジの正直表示・fail-closed は
  上限に当たった状態でも維持される**（誠実さの機構を上限の裏に隠さない）

### Q-6 見えていない領域の正直さ

- **Q-6-1** 未接続データ源に依存する問いには、`spec/04` の定型で答える:
  「そこはまだ見えていません。◯◯を接続すると見えるようになります」
- **Q-6-2** 定型応答の「◯◯」は、**その問いに実際に必要なコネクタ名**であること
  （固定文言のべた書きでなく、カバレッジ状態から導出される）
- **Q-6-3** ベースライン未成立の指標について**断定しない**。確度が明示される
- **Q-6-4** 「データが無い」と「平常だった」を混同した回答を返さない（禁じ手6）。
  陰性コントロール: events が0件の会社に「先月の売上はどうだった？」と聞いて
  **「平常でした」と答えたら即 fail**

### Q-7 還流（dialogue → narratives）

- **Q-7-1** 質問と回答が `events` に `event_type='dialogue'` / `sensitivity='S3'` で記録される
  （Q-D5。`00001` の CHECK 制約に `dialogue` は既に含まれている）
- **Q-7-2** `events` に本文用の**新規カラムを追加しない**（本文は `metrics` に入れる）。
  `EVENTS_ALLOWLIST`（`scripts/check-allowlist.ts`）に違反しない
- **Q-7-3** 質問から抽出された懸念・意図が narratives に upsert される。
  **記銘は `spec/02` の3経路のみ**。自由文の追記経路を新設しない
- **Q-7-4** 経営者の訂正（「それは違う」）が narratives の confidence を即時減算し、
  **訂正自体も dialogue イベントとして残る**（監査可能性）
- **Q-7-5** 質問内容が Sense 層の検知スコアに影響を与えない
  （較正信号の制限。`spec/03`「較正信号に含めてはならないもの」の趣旨を先取りして守る）

### Q-8 体験（Web UI）

- **Q-8-1** ログイン済み画面から質問でき、回答と証拠参照が同一画面で読める
- **Q-8-2** 回答生成中の状態が分かる。無反応の白画面にしない
- **Q-8-3** 空状態とエラー状態が見た目で区別できる（スライスA A-3-1 と同基準）
- **Q-8-4** ユーザー向け文言に内部コード（`RLS_VIOLATION` / `42703` 等）が出ない（A-3-2 と同基準）
- **Q-8-5** デザインは「静かな計器板」方向性に従う
  （オフホワイト＋インク黒＋深い藍。グラデーション／ネオン／紫系AI配色は禁止。A-3 の確定事項）
- **Q-8-6** 文言はi18n辞書経由（A-3-4 と同基準）

### Q-9 セキュリティ（固定基準・スライス1 F と同一）

- **Q-9-1** トークン・秘密が回答本文・ログ・イベントに混入しない
- **Q-9-2** 新テーブルを作る場合は RLS ポリシーとセットで作り、`00013` の検証リストに追記する
  （追記漏れはエラーにならず静かに全公開になる。gotchas 実績）
- **Q-9-3** gitleaks 検出ゼロ
- **Q-9-4** 質問文をそのままプロンプトに連結する経路で、**指示注入で他社データや
  システムプロンプトを引き出せない**ことを陰性コントロールで確認する
