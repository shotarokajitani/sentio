## 【2】(b) の決定 — 案A を採る。ただし単独では採れません

**あなたが「安全弁が1本減る」と書いた箇所は、こちらで穴の位置まで特定できました。**

`ci.yml:2` は `on: [pull_request]` **のみ**です。したがって:

| 経路 | ci.yml（integration + check:allowlist） | deploy.yml verify |
| --- | --- | --- |
| PR 経由の merge（squash 含む） | **走る** | 走る |
| main への直 push | **走らない** | 走る |

案A を単独で採ると、**main 直 push の経路で `check:allowlist` が一切走らなくなります。**
これは CLAUDE.md 絶対規則「S2テーブルに本文型カラムを追加しない」の機械的担保が
その経路で消えることを意味します。`deploy.yml:12` のコメント
「mainへの直pushやsquash mergeでCIをスキップした場合の安全弁」は、まさにこの穴を塞ぐためのものです。

なお squash merge は PR があるので `ci.yml` が走ります。**穴は直 push だけです。**

### 決定

**案A を採用し、同時に main のブランチ保護（直 push 禁止・PR 必須）を前提条件にします。**
直 push 経路そのものを消せば、安全弁は不要になります。

あなたの作業:

1. `deploy.yml` の `verify` から `check:allowlist` を外す
2. 外した理由を**その場にコメントで残す**。最低限これを書くこと
   - 実DB照会になったため `ci.yml` の `integration` が担う（`ci.yml:48` と対応）
   - **`ci.yml` は `on: [pull_request]` のみ**であり、この分担は
     **main への直 push が禁止されていることに依存する**
   - ブランチ保護が外れた場合、S2 allowlist の担保が直 push 経路で消える
3. ブランチ保護の設定は**人間作業**です。梶谷さんへの依頼文案を
   `docs/` の適切な場所に用意してください（設定項目名まで具体的に）。
   CLAUDE.md「人間作業のバッチ化」に従い、この時点では依頼せず貯めること
4. **ブランチ保護が入るまで merge しない。** これを merge 前チェックリストに追加すること

案B（`deploy.yml` に `supabase start` を足す）を採らない理由は、
`ci.yml` の integration ジョブ一式（`db reset` / `status -o env` / マスク処理）を
