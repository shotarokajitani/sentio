## **崩れた見立て: ③④⑥ は同じ検出器から出ている**

説明文を見れば分かる。

| 仕込み | 説明文 | 出所 |
| --- | --- | --- |
| #3 reply_delay | `Reply time worsening: …` | `scanMetricChange` の抽出器 `communication` |
| #4 overtime_creep | `Overtime hours increasing: …` | `scanMetricChange` の抽出器 `attendance` |
| #6 inquiry_decline | `Inquiry count declining: …` | `scanMetricChange` の抽出器 `web` |

**3件とも `scanMetricChange`（`src/sense/scanner.ts:194-236`）の出力である。**
この関数は直近5点が**すべて同方向に動いているか**を見ており、
説明文にも `(N consecutive points)` と書く。**現象としては trend である。**
にもかかわらず 226行目は `scanType: "deviation"` と名乗る。

ところが**仕込み側の期待は割れている。**#3 と #6 は `deviation` を期待し、#4 だけ `trend` を期待する。

> **したがって「④を trend と名乗らせる」を単独で行うと、④は○になるが③と⑥が×になる。
> 5/7 → 4/7 に下がる。** `07_open_items` の判断1は、この副作用込みで選ぶ必要がある。

## 誤検知1件の正体

```
trend: Rising trend over 4 periods
```

`scanTrend` が**正常データの revenue** で4連続上昇を拾っている。
`TREND_MIN_PERIODS = 4`（=5点）は、上下する売上に対して低すぎる。
案Bを採ると `scanMetricChange` 由来の候補も `trend` を名乗るため、
**誤検知の見え方も変わる。**閾値と併せて見る必要がある。

## 併せて見つけた欠陥（未修正）

`scanTrend` の `trendIds` は、**方向が反転したときにクリアされない**（`scanner.ts:92-110`）。

```ts
if (curr < prev) { consecutiveDown++; consecutiveUp = 0; trendIds.push(...); }
else if (curr > prev) { consecutiveUp++; consecutiveDown = 0; trendIds.push(...); }
else { consecutiveDown = 0; consecutiveUp = 0; trendIds.length = 0; }  // 等値のときだけクリア
```

カウンタは 0 に戻るのに証拠IDは積まれ続けるので、
**発火したとき `evidence_event_ids` に逆方向の期間のイベントが混ざる。**
評価スイートは証拠の交差で採点するため、**この欠陥は検知数を実際より多く見せうる。**
今回の run では誤検知候補がどの仕込みとも交差しなかったので影響は出ていないが、
**データが変われば出る。**
