2. **`retention-purge` の cron を張る**

## cron の置き方（決定）

**新しい `cron.schedule` を張る。ディスパッチャに相乗りさせない。**

契約CD の CD-D2「cron はディスパッチャだけを叩く」は、
**`deliver-*` が `email` を必須にしているため**の決定だった。
`retention-purge` は**全社を1回で回す関数で、会社ごとの引数を取らない**
（`retention_expired_companies` RPC で対象を引く）。**CD-D2 の理由が当てはまらない。**

`dispatch-daily` のループの中に入れると、**会社ごとに全社削除が走る**ことになり誤りである。

- ジョブ名: `retention-purge`
- 時刻: **UTC 20:00 毎日**（JST 05:00）。`dispatch-daily`（22:00 UTC）の2時間前。
  KING OF TIME の接続禁止帯（JST 8:30–10:00 / 17:30–18:30）に掛からない
- 本文は `00020` / `00028` と同じ形にする。**`read_vault_secret_by_name` 経由**で、
  秘密の値を migration にもログにも書かない
- 冪等性: `cron.schedule` は同名ジョブを上書きする。再実行安全であることを冒頭に書く

**`retention-purge` が空の本文（`'{}'::jsonb`）で動くことを、先に実測で確かめること。**
`deliver-*` は `email` が無いと 400 を返した。**同じ罠を踏まないため、実装前に1回叩く。**
確かめずに cron を張ると、毎日エラーが積み上がって誰も気づかない。
