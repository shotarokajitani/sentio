## 2. なぜ検証が効いていないのか

`deploy.yml` は素の `supabase functions deploy <name>` を使っており、
`--no-verify-jwt` は**付けていない**（`deploy.yml:99`）。
`supabase/config.toml` には `[functions.*]` の節が**1つも無い**（grep で0件）。

つまり**どこにも「検証を有効にする」設定が存在しない。**
フラグを外したのに効かないのではなく、**有効化する側の設定が無い。**

## 3. いま守っているもの

**`resolveCaller`（`supabase/functions/_shared/caller.ts`）の一層だけ。**

- fail-closed。判定できないものは 401 を返す
- **漏洩はしていない。** 認証情報の無いリクエストは実データに到達しない（実測）
- 全18本が `resolveCaller` を通っていることは `check:caller-guard` が CI で機械検査している
  （PR #47 の実行で「18本すべて resolveCaller」を確認）

**危険なのは一層であること自体ではなく、二層だと思い込んでいたことだった。**
その誤認は `deploy.yml` のコメントと本ファイルで既に潰してある。

## 4. 選べる道

| 案 | 内容 | 評価 |
| --- | --- | --- |
| **A** | **一層のまま**。`resolveCaller` を唯一の認証境界と明示し、`check:caller-guard` をその保証と位置づける | 追加コスト0。**いま既にこの状態**。宣言と実態が一致する |
| **B** | `resolveCaller` の手前に別のガード関数を置く | **二層に見えて一層。** 同じワーカー・同じデプロイ・同じコードベースなので、片方が壊れる状況ではもう片方も壊れる。防御の深さは増えない |
| **C** | 別プロセス（プロキシ等）を立てて本当の二層にする | 本物の二層だが、運用対象が1つ増える。SME向け1人開発の規模に対して重い |
| **D** | `config.toml` に `[functions.*] verify_jwt = true` を書いてゲートウェイ検証を有効化する | **採れない。** Supabase 公式が「Edge Functions は `anon` / `service_role` の **JWT ベースのキーでしか** JWT 検証が動かない」と明記しており、内部呼び出しは新形式 `sb_secret_...` を使っている。有効化すると**内部呼び出しが全部弾かれる**（cron・invoke-function・Day0 が止まる） |

**D が採れないことが、この項目の実質的な結論である。**
新形式へ移った以上、ゲートウェイ JWT 検証は内部呼び出しには使えない。
2026年末の廃止期限に追われる理由も無くなった（**移行はもう済んでいる**）。

## 5. 判断が要る点（**人間**）
