# 報告した変更が、実物に入っていることを確かめる

**「直した」と報告したのに実物に入っていなかった**形を止める。
`hooks-coverage.md` / `ci-coverage.md` と同じく、**守れる範囲と守れない範囲**を書く。

## なぜ作ったか

2026-09-01 に2回起きた。どちらも「作業した」と報告され、**実物には入っていなかった**。

| #   | 事象                                                               | 何が起きたか                                                                                            |
| --- | ------------------------------------------------------------------ | ------------------------------------------------------------------------------------------------------- |
| 1   | PR #57 を merge したと報告されたが `origin/main` に無かった        | `mergedAt` も `mergeCommit` も `null`。**一度も merge されていなかった**（巻き戻しでも close でもない） |
| 2   | ローンチ門の表記を更新したと報告されたが、置換が当たっていなかった | インデント違いで文字列が一致せず、**0件置換のまま「更新した」と報告した**                               |

**どちらも CI では捕まらない。** 変更が入っていないのだから、テストは何事もなく緑になる。
`.claude/rules/ci-coverage.md` の残存制約1「赤い CI を読まずに完了報告する経路は止められない」
と同じ層の問題で、**規則の追加ではなく履行の問題**である。

## 置換の手段によって挙動が違う（ここが今回の落とし穴）

**「成功した」が「一致した」を意味するとは限らない。**

| 手段                           | 0件一致のとき                                            |
| ------------------------------ | -------------------------------------------------------- |
| Claude Code の `Edit` ツール   | **失敗する。** `old_string` が一致しなければエラーになる |
| `str.replace()`（Python / JS） | **黙って何もしない。** 例外も戻り値の変化も無い          |
| `sed -i`                       | **黙って何もしない。** 終了コードは 0                    |
| `git apply` / `patch`          | 失敗する                                                 |

2026-09-01 の #2 は Python の `str.replace()` である。
**手段を変えた瞬間に安全網が外れることに気づいていなかった。**

## 作法

### 1. 文字列置換で書き換えたら、当たったことを機械で確かめる

`Edit` 以外の手段（`str.replace` / `sed` など）を使うときは、**置換ごとに一致を主張する**。

```python
def sub(old, new, label):
    global s
    assert old in s, f"未一致: {label}"   # ← これが無いと 0件置換に気づけない
    s = s.replace(old, new, 1)
```

書き終えたら、**対象語が消えていること・新しい語が入っていること**を `grep` で確かめる。

```
$ grep -rn "北極星" --include=*.md .     → 0件
$ grep -c "fallbackScheduleHeading" src/i18n/ja.ts → 1
```

### 2. merge したと報告する前に、実物が main に入ったことを確かめる

PR の状態ではなく、**コミットが `origin/main` の祖先か**を見る。

```
$ git merge-base --is-ancestor <sha> origin/main && echo 含まれる || echo 含まれない
$ git show origin/main:<path> | grep <新しい語>
```

`gh pr view` の `state` だけでは足りない。`mergedAt` / `mergeCommit` まで見る。

### 3. デプロイまで報告するなら、全ジョブの結論を引用する

`deploy.yml` は3ジョブある。総合の色だけでなく、**どのジョブが何秒走ったか**を出す。
skip されたジョブがあれば、それは「走らなかった」であって「通った」ではない。

## 守れない範囲（設計上の限界。これは仕様であって不具合ではない）

1. **機械では止められない。** これは検査器ではなく作法である。
   `assert` を書き忘れれば同じことが起きるし、書き忘れたことを検出する仕組みは無い。
   **CI に載せられる形ではない**——変更が入っていないコードは、テストから見れば
   単に「変更前の正常な状態」だからである
2. **grep での確認は、意図どおりかまでは見ない。**
   語が入っていることは確かめられるが、**入るべき場所に入ったか**は見ていない。
   別の箇所に紛れ込んでいても緑になる
3. **人間（または私）が確認を省けば、それまでである。**
   `.claude/rules/ci-coverage.md` の残存制約1 と同じで、
   担保は CLAUDE.md 常設指示「実行せずに『完了』と報告しない」であり、
   **その規則は既に存在し、守られていなかった。**
   ここに書いたのは、守るための具体的な手順である
