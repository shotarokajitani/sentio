# スライスWM — 週次メールを `/report` と同じ集計に寄せる

- 状態: **active**（2026-08-29 梶谷さん承認）
- 起草: 2026-08-29（検収者）
- 前提: スライスW クローズ済み（`docs/contracts/slice-weekly-report.md`）

## なぜやるか

**「今週の会社」を名乗るものが2つあって、片方は構造的に空である。**

| | 出所 | 実際に出るもの |
| --- | --- | --- |
| `/report`（画面） | `events` を直接読む（W-D2） | 会議 5件 / 総会議時間 5時間 / のべ出席者 3人 ＋ 予定5件（2026-08-28 実測） |
| `deliver-weekly`（メール・件名 `[Sentio] 今週の会社`） | **`baselines` を読む**（`index.ts:81`） | 「**基準値はデータ蓄積後に確立されます。**」（`index.ts:136`） |

`baselines` は `is_established: false` / `observation_count: 0`（2026-08-27 実測）。
**メール側は、データがあってもなくても同じ文しか出せない。**

スライスW は同じ問題に当たって **W-D2 で「`baselines` を使わない。`events` を直接読む」** と決め、
それで実データが出た。**その判断をメールに横展開していないだけである。**

新しいデータも新しいスコープも要らない。`events` は既にある。

## セルフチェックで見つけた落とし穴（2026-08-29・起草者）

契約を書いたあとに自分で読み直して見つけたもの。**着手前に潰すこと。**

### 1. 週の定義が2つある（**一番危ない**）

- `/report` は `jstWeekRange`（**JST の月曜00:00 起点**・W-1-1）
- `deliver-weekly` は `resolveWeeklyPeriod`（**ISO週の文字列**。`_shared/delivery.ts`）

**この2つが同じ週を指す保証を誰も確かめていない。**
ISO週の算出がどのタイムゾーンで行われているかによって、
**週の境界（日曜深夜〜月曜早朝）でメールの見出しと数字がずれる。**

冪等キーは `weekly:<company_id>:<ISO週>` なので、
**ここを勝手に変えると過去の配信記録と衝突する。**

**やること**: `resolveWeeklyPeriod` の実装を読み、`jstWeekRange` と**同じ週を指すか実測する**。
ずれるなら、**どちらに寄せるかは人間の判断**。止まって報告すること。

### 2. `target_week` を無視してはいけない

`deliver-weekly` は `target_week` の明示指定を受け付け、導出より優先する
（`now` 依存で JST 日付境界をまたぐと1週ずれるため。冪等な再実行の担保）。

`summarizeWeek(rows, reference)` は `reference: Date` を取る。
**`target_week` が来たときは、それに対応する日付を `reference` に渡すこと。**
`new Date()` を渡すと、指定した週と違う週の数字が入る。

### 3. `select("*")` を書かない

`deliver-weekly/index.ts:93-96` のコメントが理由を書いている。

> `*` のままだと `check:schema`（S-5-1）が参照列を静的に読めず、
> 列の消失・改名を検出できない穴になる

`period_start` / `period_end` / `metrics` / `source` / `event_type` を**列名で明示して**取ること。

### 4. このスライスでは「届く」ようにはならない

`cron.schedule` が張られているのは `sync-connections` だけである（`00018` / `00020`）。
**週次メールは今も手動起動（`invoke-function`）でしか動かない。**

このスライスは**中身**を直すもので、**配信の自動化は A-2 の範囲**である。
完了報告で「週次メールが届くようになった」と書かないこと。書けるのは
「手動で叩いたときに実データが載るようになった」まで。

## 着手前ゲートの実測（2026-08-29）

契約が「着手前に潰すこと」と書いた2件を、実装より先に実測した。**どちらも通った。**

### 落とし穴1: 週の定義は2つとも同じ週を指す（**ずれていない**）

`jstWeekRange`（JST 月曜00:00 起点）と `isoWeekKey`（`_shared/jst.ts`・JST 基準の ISO 週）を
2025-01-01 〜 2027-12-31 で突き合わせた。

```
走査点 26280 / 週内不一致 0
境界検査: 外側でキーが変わる 1095 / 変わらない 0
```

1時間刻みの26,280点すべてで、`jstWeekRange` が返す週の**内側では ISO 週キーが一定**であり、
**境界の外では必ず変わる**（1,095日すべて）。両者は同じ週境界を持つ。

**したがって冪等キー `weekly:<company_id>:<ISO週>` は変えない。** 人間の判断を仰ぐ必要は生じなかった。

ただし `resolveWeeklyPeriod` は `now - 24h` から導くため、
**対象週は「いま」の週とは限らない**（JST 月曜に叩くと前週になる）。
そこで本文の数字は `period` から導いた基準時刻で集計する（落とし穴2 の `weekReference`）。
これで**件名の週と本文の数字が構造的に一致する**。

### WM-D1: 共有配置は Next と Deno の両方から読める（**可能**）

`src/lib/report/weekly.ts` → `shared/report/weekly.ts` へ移した（コピーは作っていない）。
Next 側は `@shared/report/weekly`、Deno 側は `../../../shared/report/weekly.ts` で同じ実体を読む。

`_shared/weekly-sections.ts` 経由で `shared/report/weekly.ts` が推移的に型検査されている。

## この契約が閉じたら分かること

いま「出力が薄い」原因は3つ混ざっている。

1. **出力が `baselines` を読んでいる**（構造的に空）
2. データが薄い（12ヶ月で15〜20件）
3. 文面の設計

**このスライスは1だけを潰す。** 潰したあとに残る薄さが、2と3の実際の大きさである。
**切り分けができるようになることが、このスライスのもう一つの成果物である。**
