## 読み

**特定の機能の回帰ではない。** 落ちる対象が試行ごとに移動し、
観測値が毎回 **503（Service Unavailable）**である。
これは Supabase Edge Runtime が**まだ当該 Function を起動していない**ときの応答の形。

- 試行1で落ちた `scan` は試行2では通った
- `scan` は `_shared/{cors,supabase-client,caller,db,baseline-stats}.ts` しか読まず、
  PR #35 が触ったもの（`retention.ts` / `00025` / `00026`）に**一切依存していない**
- したがって「#35 が `scan` を壊した」ではない

**なぜ今になって出たか（推測。未確定）**: PR #35 で `retention-purge` が増え、
デプロイ対象の Function が **18本**になった（`check:caller-guard` の出力で確認できる）。
ローカル Edge Runtime が起動を抱える本数が増え、
最初の呼び出しが冷えている窓が広がった可能性がある。**実測で確かめていない。**

## 既存の防御では足りていない

`ci.yml` の `Probe Edge Runtime reachability`（契約 S-5-2）は通っている。
つまり**「Edge Runtime に到達できるか」は見ているが、「個々の Function が
応答できる状態か」は見ていない。** 起動待ちの穴はこの間にある。

> **撤回。この節は 2026-08-23 に無効化された。**
> 同じ節の末尾に書いた無効化条件 —「**同じ 503 が再発したらこの案は外れ**であり、
> その時点で組み直す」— が満たされたためである（run `32593001376` / PR #18）。
> **この件は open item に戻っている。** 下の「再オープン」を読むこと。
>
> 撤回するのは「フレークを塞いだ」という位置づけだけである。
> **プローブの全 Function 化と 000 バグの修正はそのまま残す。**
> 前者は 18本の応答を事実として記録し、後者は到達不能を検出できるようにした。
> どちらもフレークとは独立に正しい。

`ci.yml` の `Probe Edge Runtime reachability` を**全 Function に広げた**。
テストのコードは1行も触っていない。実装は同ファイルのステップ本体を参照。

| 決めたこと | 値 |
| --- | --- |
| 対象 | `supabase/functions/*/` の実物を列挙（`_shared` は除く）。**本数をワークフローに書かない** |
| プローブの方法 | `OPTIONS` ＋ `Authorization: Bearer <service_role>`。18本すべてが CORS 分岐をハンドラ先頭に持つので、認証にもDBにも触れずに 200 が返る |
| 503 のとき | 2秒間隔でリトライ。1本あたり30回、全体420秒を上限とし、**超えたら `::error::` で赤にする** |
| 000 のとき | 従来どおり即 `exit 1` |
| ログ | 何本を何秒で起動できたか、起動待ちが発生した本数、503 を踏んだ総回数 |

**POST にしなかった理由**: service_role を付けた POST は本物の処理を走らせる。
この直後の integration テストが見るDBの状態を、プローブが先に動かしてしまう。
`OPTIONS` は 18本すべてで `req.method === "OPTIONS"` → `200 "ok"` を先頭に持つため副作用がない。

**A（テスト側リトライ）を採らなかった理由**: 本物の失敗も待ってしまう。
**C（再実行で回す）を採らなかった理由**: 赤の意味が薄まる。

### 何を温めているのか（機序は未確定）

`supabase/config.toml` は `[edge_runtime] policy = "oneshot"` である。
**ワーカーはリクエストごとに作り直されるので、プローブはワーカーを温めていない。**
温まるのはコンテナ内の Deno モジュールキャッシュ（各 Function の依存グラフの初回解決）である。
これが 503 の機序だという確証は無い。実測できるのは CI の色だけなので、
**同じ 503 が再発したらこの案は外れ**であり、その時点で組み直す。

### 併せて直した既存のバグ

従来のプローブは到達不能を検出できていなかった。

```
code=$(curl -s -o /tmp/probe.txt -w '%{http_code}' ... || echo "000")
```

curl は失敗時にも `%{http_code}` として `000` を出すため、`||` の分と連結して
`code` は `000000` になる。したがって直後の `[ "$code" = "000" ]` は**一度も成立しない**。
Edge Runtime に到達できなくてもこのステップは緑を返していた。
終了ステータスを代入とは別に見る形に直した（2026-08-23 に偽サーバで実測）。

## 陰性コントロール — 壊れたときに赤くなることの実測（2026-08-23）

プローブが緑を返しても、**壊れたときに赤くなる**ことが確かめられていなければ
「守られている」とは言えない。PR #36 の attempt 1〜4 は 503 を1回も踏んでおらず
（4回とも `起動待ちが発生した Function 0本 / 503 を踏んだ総回数 0回`）、
リトライ経路・上限超過の分岐・000 の判定はいずれも CI 上で未実行のままだった。

一時コミットで壊し、実物のログを回収してから revert した。

### 1. 存在しない Function は 503 ではなく **404** を返す（狙いは外れたが本物の陰性コントロール）

対象一覧に `__probe_negative__` を1本足した（commit `dde3759`、run `32590888865`）。
**期待は「503 リトライが上限に達して赤」だったが、実際には 404 が返った。**

```
対象 19本: day0 deliver-alert deliver-pulse deliver-weekly ingest-calendar ingest-csv
          ingest-monitor ingest-s0 investigate onetap-calendar retention-purge run-sense
          scan state-baselines state-memory-packet state-narratives state-summary
          sync-connections __probe_negative__
day0: 200（2秒）
deliver-alert: 200（0秒）
…（18本すべて 200）…
sync-connections: 200（1秒）
##[error]__probe_negative__: OPTIONS に 404 を返した。起動待ち（503）でも到達不能（000）でもない
```

**分かったこと。** Edge Runtime は「Function のディレクトリが無い」を 404 で表す。
503 は「起動しようとして失敗した／まだ起動していない」であって、
**存在しないものへの応答ではない。** したがって存在しない Function 名では
リトライ経路にも上限超過の分岐にも入らない。

**それでも陰性コントロールとしては本物である。**
発火したのは「200 でも 503 でもない応答を弾く」分岐であり、
これが無ければプローブは 404 を握りつぶして緑を返していた。
**プローブが何も温めていないのに緑になる形**を、この分岐が実際に止めることが実測できた。

狙った上限超過の分岐は、実 HTTP で 503 を作り直して別に実測した（次節）。

### 2. 実 HTTP の 503 → 上限超過で赤

503 を返し続ける偽サーバを CI 内に立て、プローブの向き先を一時的にそこへ変えた
（commit `26bc9ac`、run `32591493324`）。**上限値は変更していない**
（`MAX_ATTEMPTS=30` / `SLEEP_SEC=2` / `BUDGET_SEC=420`）。

```
対象 18本: day0 deliver-alert deliver-pulse deliver-weekly ingest-calendar ingest-csv
          ingest-monitor ingest-s0 investigate onetap-calendar retention-purge run-sense
          scan state-baselines state-memory-packet state-narratives state-summary sync-connections
【陰性コントロール1-b】向き先を http://127.0.0.1:8599 に変えた（常に 503 を返す偽サーバ）
##[error]day0: 503 が 30回続いた（2秒間隔 / 58秒）。起動待ちの上限を超えた
応答本文:
##[error]Process completed with exit code 1.
```

リトライが実際に 30回回り、上限に達して `::error::` を出し、`integration` が赤で終わった。
**503 を握りつぶして緑にする形にはなっていない**ことが実測できた。

**このとき踏んだ落とし穴を1つ残す。** バックグラウンドに立てたサーバがステップの
stdout を掴んだままだと、スクリプトが終了してもランナーが EOF を待って固まる
（ローカルで3分ハングして実測）。`>/dev/null 2>&1 &` で fd を切り離し、
`trap ... EXIT` で必ず落とす形にした。
**この偽サーバは一時コミットのものであり、本来のワークフローには1行も残っていない**
（復元後の `git diff origin/main -- .github/workflows/ci.yml` で確認済み）。

### 3. 到達不能（000）→ 即 `exit 1`

プローブの向き先を待ち受けていないポートへ一時的に変えた
（commit `4f5dcd7`、run `32591796972`）。

```
対象 18本: day0 deliver-alert deliver-pulse deliver-weekly ingest-calendar ingest-csv
          ingest-monitor ingest-s0 investigate onetap-calendar retention-purge run-sense
          scan state-baselines state-memory-packet state-narratives state-summary sync-connections
【陰性コントロール2】向き先を http://127.0.0.1:1 に変えた（待ち受けなし）
##[error]day0: Edge Runtime に到達できない（curl 失敗）。supabase start が functions を配信していない
##[error]Process completed with exit code 1.
```

タイムスタンプは `18:50:53.2686822`（向き先の変更）→ `18:50:53.2799960`（`::error::`）で
**11ミリ秒**。リトライも待ちも入らず、その場で落ちている。

**これは上の「併せて直した既存のバグ」の、CI 上での証明にあたる。**
`$(curl ... || echo "000")` のままなら `code` は `000000` になり、
`[ "$code" = "000" ]` が成立せず、次の `!= "503"` の分岐に落ちて
「OPTIONS に 000000 を返した」という別のメッセージになっていた。
到達不能として正しく判定できていることが実測できた。

### 未実測のまま残っている分岐

上の1〜3で発火させたのは次の3つである。

| 分岐 | 実測 |
| ---- | ---- |
| 200 でも 503 でもない応答を弾く | 済（404 で発火。run `32590888865`） |
| `MAX_ATTEMPTS` 超過で赤 | 済（503×30回 / 58秒で発火。run `32591493324`） |
| 000（到達不能）で即 `exit 1` | 済（run `32591796972`） |

**`BUDGET_SEC=420`（全 Function の総待ち時間の上限）の分岐だけが未実測である。**
陰性コントロール2 では 1本目が 58秒で `MAX_ATTEMPTS=30` に先に当たったため、
総待ち時間の判定に到達しなかった。

この分岐を踏ませるには「1本あたりは上限未満だが、積み上げると 420秒を超える」状態が要る。
`MAX_ATTEMPTS` を変えずに作るには 8本以上が同時に長く 503 を返す必要があり、
今回の一時コミットの範囲では作れなかった。
**追加実測は不要と判断した（2026-08-23・梶谷さん）。**
ここに未実測として残すのは、後から「全部確かめてある」と誤読されないためである。

### 機序の読みが崩れた

上の「何を温めているのか」では、プローブが温めるのは Deno モジュールキャッシュだと書いた。
**モジュールキャッシュは run 1 と run 2 の間で消えない。**
run 1 が緑で run 2 が赤なら、コールドスタートでも温まり不足でも説明がつかない。

より整合するのは「503 は起動待ちではなく、**ワーカー生成そのものの失敗**
（連続実行によるリソース枯渇、または並列実行時の競合）」という読みである。
プローブが 18本を直列に軽く叩いて `0本 / 0回` を返すのに、テストは 503 を踏む。
**プローブとテストは別の条件を見ている**ことの直接の証拠になっている。

ただしこれもまだ**仮説である**。今日この件では、材料を見ずに仮説を立てて2回外している
（「存在しない Function は 503 を返すはず」→ 実際は 404、
「プローブが温めれば塞がる」→ 再発）。**次は材料を見てから立てる。**

### 再測の順序（2026-08-23・梶谷さん指定）

1. **赤のときの Edge Runtime のコンテナログを回収する。**
   仮説を変える前に、503 のとき何が起きているかを実物で見る
2. **vitest の並列度を落として再現が消えるかを見る**（`--no-file-parallelism`）。
   integration は9ファイルあり、`policy = "oneshot"` はリクエストごとにワーカーを
   作り直すので、ワーカー生成が一点に集中する。
   消えればリソース枯渇／競合が原因だと直接言える
3. その後で `policy = "per_worker"` を試す。**これは対策であって原因の特定ではない**

**`Run integration suite 3 times` を1周に戻すことはしない。**
連続実行によるリソース枯渇が候補である以上、周回を減らすのは再現条件を弱める方向で、
赤が出なくなって「直った」に見える。却下した案C と同じ罠になる。
