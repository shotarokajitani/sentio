## タスク1：CLAUDE.md の禁じ手条文を差し替える

禁じ手の一覧の中に、連携先の収益に関する条文がある場合、または存在しない場合のいずれでも、以下の条文を**採用版として記載**する。

**削除・不採用（もし存在すれば）**

```
連携先の導入・販売で収益を得ない
```

**採用**

```
観測と提案を分離する。
収益の有無は、何を検知し何を問うかに一切影響してはならない。
提案に自社の収益が伴う場合は、必ず提案本文で開示する。
```

制約：CLAUDE.md は200行以内を維持する。行数が超過する場合は、詳細を `docs/spec/` 側に逃がし、CLAUDE.md には条文本体と参照先のみを残す。

## タスク2：spec/02（データ接続レイヤー）の改訂

### 2-1. 非スコープの明記

以下を「非スコープ」として明記する。禁じ手ではなく、対象外である旨を区別して書くこと。

- 個人LINE（1:1・グループ）
- LINE公式アカウントを Ingest コネクタとして使用すること
- Facebook Messenger / Instagram DM
- 「顧客接点層」というコネクタ分類そのもの

判断根拠として、以下を要約して併記する。

- 個人LINEの自動取得はLINE利用規約により不可
- LINE WORKS の監査ログダウンロードは有償プラン限定・保存6ヶ月。フリープランは30名上限であり、ターゲット層のカバーにならない
- Messenger / IG DM は pages_messaging・business_management 等の App Review が必要で、対象母集団（税理士チャネル経由の製造・建設・小売）と合致しない

### 2-2. コネクタ優先順位の改訂

```
旧：カレンダー・会計 → Slack／Chatwork → Gmail

新：会計
  → カレンダー（Google ＋ Microsoft 365）
  → 勤怠
  → メール（Gmail ＋ Outlook）
  → Slack／Chatwork（加点要素）
```

Slack／Chatwork は必須ではなく「あれば精度が上がる加点要素」である旨を明記する。**チャットコネクタがゼロでも成立するのが正規構成**であることを、欠損ではなく設計前提として書くこと。

### 2-3. capability 概念の導入

コネクタに以下の属性を持たせる定義を追加する。

| capability | 意味 | 該当 |
|---|---|---|
| `full_metadata` | 社内全体のメタデータが取得できる | Slack / Chatwork / LINE WORKS（有償） |
| `partial` | 一部のみ取得できる | LINE WORKS（フリー） |
| `none` | 接続手段が存在しない | 個人LINE |

### 2-4. Microsoft 365 コネクタの追加（設計枠のみ）

**実装はしない。** spec上の設計枠として以下を記載する。

- 取得手段：Microsoft Graph API
- 取得対象：Outlook予定表、Teams会議、メールのメタデータ
- 前提：Azure AD アプリ登録＋管理者同意
- 優先度：勤怠より上位
- 詳細仕様は指示書 #02 の調査結果を受けて次セッションで確定する旨を注記

## タスク3：spec/03（検知エンジン）の改訂

### 3-1. パターンE・F をチャット非依存に再定義

現行のチャット依存の検出定義を、以下の代替に置き換える。**閾値やロジックの詳細は次セッションで確定するため、検出元データの対応表までを記載し、未確定である旨を明記すること。**

| シグナル | 旧（チャット依存） | 新（チャット非依存） |
|---|---|---|
| 特定個人の孤立 | 発言数の減少 | カレンダー：1on1・定例の消滅 ／ 勤怠：連続休暇・打刻時間の変化 |
| 現場の疲弊 | 深夜メッセージ比率 | 勤怠：特定部門の残業偏り・休憩取得の崩れ |
| 内製体制の崩れ | 会話量の変化 | 会計：外注費の急増・人件費構成の変化 |
| 社外関係の途絶 | ルーム活動停止 | カレンダー：特定取引先との接触消滅 ／ メールメタデータ：往復頻度 |

根拠として以下を記載する。

- 従業員99人以下のビジネスチャット導入率は21.6%（日経BPコンサルティング 2024年10月調査）
- 中小企業で仕事にプライベートチャットを使う層は83.6%（kubell 2024年11月調査）
- したがってチャット依存の検知設計は、ターゲット層の約8割で機能しない

### 3-2. カバレッジ概念の追加

「接続できていない」ことを欠損としてではなく、State層が保持する状態として定義する。Sense層はこれを参照する。

### 3-3. Evaluator の基準追加

```
カバレッジ不足時は断定しない
```

を評価基準に追加する。既存5基準との関係（6番目として追加するのか、既存基準の下位条件とするのか）は、既存の記述構造に合わせて判断し、判断理由をコミットメッセージに書くこと。

### 3-4. Evaluator 較正信号の制限（重要）

以下を制約として明記する。

```
Evaluator の較正信号として使用してよいもの：
  開封率・返答率・「知らなかった」率

較正信号に含めてはならないもの：
  相談ボタンの押下率
  導入支援の成約

理由：押下率を較正に用いると、意図せず「相談を誘発しやすい問い」の
スコアが上昇し続ける。事後の原因特定と巻き戻しが困難なため、
設計段階で遮断する。
```

## タスク4：spec/09（統制・プラン）の改訂

### 4-1. 相談ボタンの仕様追加

| 項目 | 仕様 |
|---|---|
| 表示条件 | Suggestion が「外部の手が要る」種別のときのみ。常設しない |
| 押下時 | それまでの文脈を要約した相談カードを生成する |
| 収益の開示 | 相談カード画面で初めて費用を提示する |
| 未押下時 | 何も起きない。催促しない。再表示は既存の間隔統制（同一ツールへの提案は2週間に1回まで）に従う |

「push 4枠 + pull 1」原則の pull 側に属することを明記する。

### 4-2. 要件A：Sense層の収益情報遮断（設計記載のみ）

以下を仕様として記載する。**hooks の実装はこの指示書のスコープ外。**

```
Sense層（シグナル検出・問い生成・Evaluator採点）は、
提携先・マージン・導入支援メニューに関するデータを参照できない。

Planner に渡すコンテキストから該当テーブルを物理的に排除し、
hooks によって機械的に遮断する。

実装タイミング：スライス1のG2受理後、該当テーブルのスキーマ確定と同時。
```

### 4-3. 価格軸に関する注記

カバレッジ軸（接続数・パターンカバレッジ）による価格設計は、ターゲット層の約8割が上位プランに到達できないため**不成立**である旨を記載する。Question頻度軸で確定させる方針を注記し、確定は次セッションとする。
