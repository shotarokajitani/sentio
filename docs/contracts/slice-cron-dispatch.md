# スライスCD — 配信の自動化（ディスパッチャ2本＋cron 2本）

- 状態: **active**（2026-08-31 梶谷さん承認）
- 起草: 2026-08-31（検収者）
- 閉じる open item: `docs/spec/07_open_items.md`「宛先未設定の会社の扱いは呼び出し元の責務」
- 更新する open item: 同「cron の HTTP 応答を誰も読んでいない」（**解かない。射程を書き直す**）

## なぜやるか

**「報告ゼロで会社の状態が浮かぶ」の“浮かぶ側”が、まだ一度も自動で起きていない。**

`cron.schedule` が張られているのは **`sync-connections` の1本だけ**である
（`supabase/migrations/00020_cron_vault_secrets.sql`。UTC 0/6/12/18）。

`run-sense` / `deliver-pulse` / `deliver-weekly` は関数として動き、本番で配信も実測できているが、
**手で叩かないと動かない。** 取り込みだけが自動で、判断と配信が手動である。
これは製品として逆立ちしている。

## 着手前に判明していた障害（**実測で確認済み・2026-08-31**）

**cron から `deliver-*` を直接叩くことはできない。**

| 関数 | 必須の引数 | 出所 |
| --- | --- | --- |
| `deliver-pulse` | `email`（無いと 400） | `supabase/functions/deliver-pulse/index.ts:46-49` |
| `deliver-weekly` | `email`（無いと 400） | `supabase/functions/deliver-weekly/index.ts:55-57` |
| `run-sense` | `company_id` | `run-sense/index.ts` の `resolveCompanyId` |

cron の本文は `body := '{}'::jsonb` を投げるだけである（`00020`）。
**そのまま張れば毎日 400 が積み上がるだけで、誰も気づかない。**
open item「宛先未設定の会社の扱いは呼び出し元の責務」が予告していたとおりである。

**したがって、あいだにディスパッチャが要る。**

## 決定

| # | 論点 | 決定 |
| --- | --- | --- |
| **CD-D1** | **宛先の正本をどこに持つか**（open item の未確定事項） | **`auth.users.email` を正本とする。新しいテーブルを作らない。** RLS ポリシー（`00019`）が `company_id = auth.uid()` なので、**会社とアカウントは 1:1 である**（`src/lib/auth/company.ts`）。宛先を別に持つと**正本が2つになり、片方が古くなる** |
| **CD-D2** | 呼び出しの構造 | **ディスパッチャを2本作る。** `dispatch-daily`（`run-sense` → `deliver-pulse`）と `dispatch-weekly`（`deliver-weekly`）。**cron はディスパッチャだけを叩く。** `deliver-*` の引数要件を cron に漏らさない |
| **CD-D3** | 対象会社 | **連携が1つ以上ある会社だけ**（`connections` に有効な行がある）。連携ゼロの会社に空のパルスを送らない |
| **CD-D4** | 宛先が取れない会社 | **`deliver-*` を呼ばない。** スキップした事実を集計に載せる。**400 を積み上げない**（open item の要求そのもの） |
| **CD-D5** | 実行時刻 | `dispatch-daily` = **UTC 22:00（JST 翌07:00）**。`dispatch-weekly` = **UTC 日曜 23:00（JST 月曜08:00）**。どちらも KING OF TIME 禁止帯（JST 8:30–10:00 / 17:30–18:30）に掛からない |
| **CD-D6** | 1社が失敗したとき | **他社を止めない。** 全社の結果を集計し、**1件でも失敗があれば non-2xx を返す**。成功だけ数えて 200 を返さない |
| **CD-D7** | cron の HTTP 応答問題（open item） | **このスライスでは解かない。** ただし**射程を書き直す**（後述）。解いたことにしない |
| **CD-D8** | 「Sentio は何も勝手に送らない」との関係 | **抵触しない。** 当該規則が禁じているのは**ワンタップの自動実行**（下書き・仮登録で停止する）であって、定期配信そのものは製品の中核である。**契約に明記して、後から読んだ人が誤読しないようにする** |
| **CD-D9** | `deliver-alert` | **このスライスでは cron を張らない。** 即時アラートは「事象が起きたとき」に出るものであり、時刻起動とは別の設計が要る |

## CD-D7 の書き直し（**穴を埋めたと誤読させない**）

open item「cron の HTTP 応答を誰も読んでいない」は**残る。**
ただし、このスライスで**性質が変わる**ので、その差分を open item に追記すること。

- **変わること**: `deliver-*` の失敗は**ディスパッチャが await して掴む**ようになる。
  ディスパッチャは自分のレスポンスで全社の結果を返し、失敗があれば non-2xx を返す
- **変わらないこと**: **cron → ディスパッチャ**の呼び出しは依然 `net.http_post` の投げっぱなしである。
  ディスパッチャが 401 や 500 を返しても cron は成功のまま回り続ける
- **唯一の検知**: **毎朝届くはずのパルスが届かないこと。**
  これは仕組みではなく人間の気づきである。**そう書く。**
  「ディスパッチャを作ったので cron の穴は埋まった」と書かない

## 停止点

- **merge しない。** PR を全緑にした時点で止まって報告する
- **本番 Ref `kwpldqbnkraftaahnpev` への CLI 直接操作をしない。** migration の本番反映は CI/CD のみ
- **`deliver-alert` に cron を張らない**（CD-D9）
- **宛先テーブルを作らない**（CD-D1）
- 会社数が増えたときの分割・タイムアウト対策は**やらない**。
  ただし**「1関数で全社を直列に回す」という限界を契約に書き残す**こと

## 既知の限界（**最初から書いておく**）

1. **1関数で全社を直列に回す。** 会社数が増えれば Edge Function のタイムアウトに当たる。
   顧客0号の1社しか居ないうちは問題にならないが、**増えた時点で分割が要る**。
   実装は `_shared/dispatch.ts` の `for (const target of targets)` で、
   1社あたり `run-sense` → `deliver-pulse` の2往復を**直列に `await`** している
   （日次の場合）。並列化も分割もしていない。**この限界は意図して残した**（停止点）。
   ディスパッチャは `auth.admin.listUsers({ perPage: 200 })` で会社を引いており、
   **201社目からは黙って対象外になる**。分割を入れるときはここも同時に直すこと
2. **cron → ディスパッチャは投げっぱなしのまま**（CD-D7）
3. **`deliver-pulse` の中身の厚さはこのスライスでは変わらない。**
   Finding が出ていないので枠は空のままである。厚さは別の問題（データ量と Scanner）

## 非スコープ（**やらない**）

- Scanner の `scanType` ラベリング修正（別スライス。`07_open_items.md` に登録済み）
- CSV 取り込みの復旧（Anthropic の workspace 発行鍵待ち。人間作業）
- `deliver-alert` の起動設計
- 宛先の複数化・受信者テーブル（CD-D1）
- cron 応答の突き合わせ（CD-D7）
- 配信内容・文面の変更

## この契約が閉じたら分かること

**「誰も操作しない日に、Sentio が実際に何を言うか。」**

いまは叩いたときだけ動くので、出力を見ているのは常に「叩いた直後の私たち」である。
毎朝勝手に届くようになって初めて、**中身が薄いことが毎日目に入る。**
それが次に何を直すべきかを決める。
